# 1. Metadata

- Title: 在 Freaktrade 仪表盘中汇总并实时查看多个策略实例（多 Bot 一页式查看）
- Author: 原视频博主（未署名）

# 2. Overview

这段视频演示了 Freaktrade（视频中发音为“free trade”/“freaktrade”）的新功能：可以把多个并行运行的交易机器人（bots）或策略实例，通过一个“主”仪表盘统一接入并在单一界面查看其实时表现。结论是：通过在网络环境中部署一份主实例作为入口，并在各个策略实例的配置文件中允许该主实例的 API 访问（修改 cores origins 等字段），配合反向代理（traffic）与 Docker 容器化部署，可以把分散在多个浏览器标签页的实时 dry-run（模拟）或 live 实例，汇总到一处进行统一监控与快速比对，从而更高效地分析哪些策略在何种市场条件下表现良好或不佳。

# 3. 按照主题来梳理

## 3.1 功能概述：为什么需要将多个 Bot 汇总到一个仪表盘

- 视频一开始说明了场景：如果你在做大量平行的机器人和策略测试，为了验证和微调这些策略，你可能会以实时市场数据（不是历史回测）运行多个模拟（dry run）或真实实例。这会导致大量浏览器标签页，每个标签页对应一个实例，想要横向对比、查找特定时间点的数据、或者判断某一市场条件下哪些策略表现好坏，都变得很难和费时。作者把这称为“难以把所有东西排成一行（line them up）”或“没有在同一个玻璃面板上看到所有性能（one pane of glass）”的问题。
- 新功能的价值在于把这些分散实例集中显示：仪表盘能在一页展示每个 Bot 的关键信息，包括胜/负场次（wins and losses）、已实现利润（close profit）、当前未平仓盈亏（open profit/loss）、当前持仓数量与允许的最大持仓、以及总体余额等。这些信息让用户能够一目了然地判断哪些策略值得深入检查，哪些需要调整或停止。
- 视频还强调了这是对实时（非回测）运行非常有用：因为你真正想要了解的是策略在当前市场条件下的实际表现，而不是历史回测的结果。统一仪表盘帮助快速识别在某个“市场事件”中表现异常的策略（不论是特别好还是特别差），从而加速调试与迭代。
- 作者把部署方式与可重复性、易扩展性（scalability）联系在一起：建议以 Docker 容器形式部署每个实例，这样可以简单地插入新的策略或新配置文件，快速把它并入仪表盘，保证可复制性并便于扩展到更多实例。
- 小结：将多个实例汇聚到一个仪表盘能显著提升监控效率、减少浏览器杂乱、并便于横向比较策略在相同实时市场环境下的表现，为策略筛选与持续改进提供实用工具。

## 3.2 环境与部署准备：Docker、反向代理（traffic）与域名管理

- 先决条件概览：作者明确提出要运行当前版本的 Freaktrade Docker 容器（视频中提到“current version of the freaktrade docker container”），并建议把所有实例置于反向代理（traffic reverse proxy）之后。反向代理带来的好处包括：用一个明确的域名访问每个实例、自动通过 SSL（证书）保护、便于在网络中引用与区分不同实例。视频中提到他使用“traffic”（可能指的是 Traefik，作者没有明确拼写，但原意是一个反向代理工具），并推荐查看他另一个教程视频来快速上手反向代理的配置。
- Docker Compose 文件的重要性：在 docker-compose 文件中基本服务定义不变，但关键在于你需要知道每个实例被反向代理后判断的“URL”或“域名”。换言之，部署时需要为每个容器分配一个能被 traffic（反向代理）解析的主机名或子域名，以便主仪表盘能够通过这些 URL 访问各个实例的 API。
- 主实例（front-end）与从实例（strategy instances）的角色分离：作者建议部署一个单独的“前端”或“主”实例（freaktrade-main），这个实例不一定要运行有意义的交易策略，其主要作用是作为你访问 Freaktrade 的落脚页或起始页面。每当你要查看整体情况时，都先访问这个主实例，然后通过它向下连接其它在网络中运行的策略实例（这些实例可能是 dry-run 或 live）。
- 域名与命名策略：作者在 docker-compose 的 labels（标签）中为主实例设置了一个可识别的名称（例如：freaktrade 和完全限定域名），以便反向代理识别并将外部访问路由到该容器。每个策略实例也要对应一个单独的域名/子域名，这样加入主仪表盘时就会用到这个 URL。
- 小结：部署时需准备好：1）运行最新 Freaktrade 容器的 Docker 环境；2）在 Docker Compose 中为每个实例分配可被反向代理识别的域名；3）使用反向代理和 SSL 来简化运维与访问；4）用一个前端/主实例作为统一入口。

## 3.3 配置关键点：如何允许主仪表盘访问其他实例的 API（修改 config）

- 配置文件的改动位置：作者指出你需要在每个策略实例的配置文件（config file）中进行一项关键修改，目的是让主仪表盘能够通过 API 访问这些从实例。具体而言，进入配置文件的底部找到“api server”或类似区域，其中有一个“cores origins”（视频中表述为“core's origins”或“cores origins”）字段。这通常默认是空的（表示一对空的方括号 []）。
- 把主实例域名加入 cores origins：你需要把你决定的“主 Freaktrade 实例”或主仪表盘的域名（即你通过 traffic 提供的 URL）填入 cores origins 的数组中。这个改动表示允许该主实例跨实例访问当前容器的 API。作者强调：这个值要在所有你想被“聚合”到主仪表盘的从实例中都设置为同样的主实例域名（也就是“会始终指向同一个主实例”）。
- API 凭证（用户名/密码）：在配置文件里还会有“api username”和“api password”的设置。作者建议不要使用默认凭证，视频中展示的是示例凭证。每个从实例需要配置正确的 API 用户名和密码（与主仪表盘在添加时输入的用户名密码相匹配），才能让主仪表盘通过这些凭证访问该实例的 API。
- 举例说明：作者展示了他一个名为“bin hv45”的策略实例配置（这是他从主 Github 页面拿的策略示例名称），以及另一个变体“hp45”。在这些实例的 config 文件中，他都在 cores origins 同样地指向他的主实例域名，从而把这些实例开放给主仪表盘聚合。视频中强调这个字段是“ticket”（关键点、门票）——没有正确设置它，主仪表盘就无法将其它实例列入。
- 小结：在每个策略实例的 config 文件里把主实例的 URL 填入 cores origins，设置好 API username/password 并保证主仪表盘使用匹配凭证访问，这样 API 间的通信就能顺利进行，达到集中监控的目的。

## 3.4 在主仪表盘上添加与命名 Bot：实践步骤与命名习惯

- 进入主仪表盘并添加 Bot 的基本步骤：
    - 登录到你部署为主入口的 Freaktrade 实例（作者举例名称为 freaktrade-main，登录后作为 landing page 使用）。
    - 在界面左上角点击 “Free Trade UI”（或页面顶栏标识）总是回到主仪表盘。
    - 在界面上会出现一个 “Add new bot” 的按钮（若你的从实例已正确配置 cores origins 与 API 凭证，点击后可添加）。这是新增其他实例到聚合视图的入口。
- 在添加时需要填写的关键信息：
    - 名称（name）：这是给在主仪表盘中显示的任意名称，可以随意命名，但作者建议使用有意义的命名约定以便辨认。
    - URL：必须是你通过反向代理公开的、指向该从实例的可访问地址（主机名/子域名）。这是最关键的一项，因为主仪表盘会通过该 URL 去与实例的 API 通信。
    - API 用户名与密码：与该实例 config 中设置的凭证匹配，否则无法通过认证。
    - 状态标识（dry / live）：用于标注该实例是模拟（dry run）还是真实交易（live）。作者强调希望大家大多数时间都在 dry run，而若有 live 实例应当谨慎。
- 作者推荐的命名约定（个人习惯）：
    - 建议把显示名命成“策略名（基础计价货币）状态”，例如“bin_hv45（USDT）dry” 或 “hp45（BTC）live”。这样在仪表盘中一眼就能识别这是哪个策略、使用哪种计价货币（state currency）以及当前是否为真实交易。
    - 命名规范便于在列表中快速区分哪些策略用的是法币（USDT/USD）还是用币对（BTC），并能区分 dry 与 live 实例，从而在分析时避免误把 dry-run 的收益解读为真实收益。
- 添加成功后的行为：
    - 当添加后，主仪表盘会尝试连接该 URL 并用提供的 API 凭证进行认证。连接状态会从红变绿（需要手动刷新仪表盘右上角的刷新按钮，界面不会自动轮询并切换状态）。一旦状态变绿，该 Bot 就会在主仪表盘的聚合视图中显示其关键信息。
- 小结：添加 Bot 的关键是确保 URL 与 API 凭证正确、命名清晰，并标注 dry/live。命名习惯能显著加速后续的辨识与分析。

## 3.5 仪表盘视图解读：哪些字段代表什么、如何用它来筛选与比较策略

![[image 23.png]]

- 仪表盘上可以同时看到多个已接入的 Bot 列表或卡片。每个 Bot 的显示通常包含以下关键信息（作者在视频中逐一描述）：
    - 名称（自定义显示名）：便于区分不同策略实例。
    - Open / Allowed（开仓数量 / 允许的最大开仓）：首个数字显示当前有多少笔开仓，第二个数字显示允许同时持有的最大仓位。这个信息表明某策略当前的持仓压力与其配置的头寸并发限额。
    - Open Profit（未实现盈亏）：当前持仓尚未平仓的总盈亏值（可以是正或负）。
    - Close Profit（已实现盈亏）：历史上已经平仓的盈利或亏损总和，这些是已经结算的收益/损失。
    - Balance（账户余额）：策略所记录或模拟的账户余额（视频中很多是 dry-run，作者特别提醒这些数字只是模拟结果）。
    - Wins / Losses（胜/负次数）：用于衡量策略在执行记录中的胜率或获利/亏损次数。
- 使用场景与分析方法：
    - 快速筛选性能异常策略：当某一策略在特定市场条件下突然出现大量负的 Close Profit 或 Open Profit，仪表盘让你迅速定位是哪个策略受到冲击，从而进一步打开该实例进行详细日志、订单或策略参数检查。
    - 找出在相同市场事件中表现良好的策略：仪表盘不仅能暴露问题，也能帮助发现哪些策略在同一波动中表现优异，便于对这些策略的参数、触发条件或风险管理做深度研究，从而把成功的做法复制到其他策略上。
    - 区别 dry-run 与 live：因为仪表盘会显示实例所标注的状态，用户在比较时必须牢记哪些是模拟数据。作者反复提醒：这些演示中的数字全部为 dry run，不能当成真实盈利保证。
- 操作提示：
    - 仪表盘不会自动刷新所有添加的 Bot 的连接状态：在添加 Bot 后需手动点击刷新，等待从红变绿表示连接成功。
    - 仪表盘提供了从一页查看多个实例的能力，但若要深度诊断某一策略，仍需跳转到对应实例的详细界面去查看日志、策略文件与交易历史。
- 小结：仪表盘用有限的几项关键指标提供整体健康度与绩效快照，使得在大量并行策略中快速定位好/坏表现成为可能，进而支持更快速的策略迭代与学习。

## 3.6 风险提示与最佳实践：dry run 优先、凭证安全与命名规范

- dry run 的必要性与风险提示：
    - 作者多次强调在测试阶段应优先使用 dry run（模拟），以避免由于策略逻辑错误或市场异常直接造成实盘损失。视频里的很多演示数据都是模拟的，他提醒观众“这些数字要带着怀疑看（take these numbers with a grain of salt）”，不要把模拟利润当成实盘回报。
    - 若确实运行 live 实例，需谨慎操作：确保风控参数、仓位限制和滑点/手续费等设置已经校准，并且严格监控首日或重大变更后的实时表现。
- API 凭证与安全：
    - 不要使用默认的 API 用户名和密码，视频中明确建议更换默认凭证，避免被未经授权的访问或误操作。当多个实例都允许主仪表盘访问时，凭证管理显得尤为重要。
    - 因为实例通过网络可被主仪表盘访问，建议所有流量均在反向代理之下并通过 SSL 加密，从而减少中间人攻击或明文凭证泄露风险。
- 命名与组织最佳实践：
    - 作者推荐在命名时包含策略名、state currency（状态货币/计价货币）和 dry/live 标签，例如：策略名（USDT）dry。这样的命名约定便于在页面快速分辨策略类型与状态，避免把模拟收益误记为实盘盈利或把不同计价货币的收益直接比较造成误判。
    - 组合化部署：以 Docker 容器化策略实例，配合统一的主入口，可以让你更容易复刻、扩展或替换策略，保持配置一致性。
- 观察与迭代流程：
    - 在识别到某策略在特定市场下表现异常时，作者建议先在 dry run 中复现或调整策略参数，然后再把改动推到少量 live 实例进行验证，从而形成安全的迭代闭环。
    - 使用主仪表盘观察多策略在相同时间窗的行为差异，作为找出“鲁棒策略（robust）”或“对特定市场条件敏感策略”的重要依据。
- 小结：以 dry run 为主、安全管理 API 凭证、采用清晰命名并把实例置于反向代理与 SSL 之下，是在使用该聚合功能时的基本最佳实践与安全防护策略。

# 4. 框架 & 心智模型（Framework & Mindset）

- Mindset：集中化监控 + 迭代驱动
    - 思路概述：将大量并行测试视为一个实验群（experiment fleet），目标不是把每个实例分别盯着看，而是通过集中化监控来快速筛选出“值得深入研究”的实验，然后针对这些实验进行有针对性的调试与迭代。这个心态强调“观察优先、局部深入”的节奏：先用仪表盘识别异常或亮点，再切入单个实例做深度排查。
    - 风险意识：优先以 dry run 验证改动与新策略，避免把初次或未经充分验证的策略直接投入实盘。对 live 实例保持更严格的变更控制与监控频率。
    - 可复制性思维：所有实例应以容器化（Docker）部署，并使用一致的配置模板（docker-compose 与 config 文件模式），以便在发现有效策略时可以快速克隆并扩展。
- Framework：集中入口 + 授权访问 + 命名与标注标准化（实施步骤）
    - 步骤一：建立主入口（主仪表盘）
        - 部署一个专门的 Freaktrade 实例作为“主仪表盘”（freaktrade-main），此实例作为你访问所有策略的起点，不一定承担交易任务，只要它能稳定暴露 UI 与调用 API 的入口即可。
        - 将主仪表盘放置在反向代理（traffic）后，分配一个固定且可解析的域名，并为其配置 SSL，以便整个内部网络能统一引用该域名。
    - 步骤二：容器化每个策略实例
        - 每个策略作为一个独立的 Docker 容器运行，配置独立的 docker-compose 内容及策略文件。容器化保证部署的一致性与快速复制。
        - 给每个容器分配一个由反向代理管理的域名或子域名（通过 labels/traefik 配置）。
    - 步骤三：在每个策略实例的 config 中允许主仪表盘访问
        - 编辑每个从实例的 config file 中的 api server 部分，把主仪表盘的 URL 填入 cores origins（或相关字段），以允许跨实例 API 调用。
        - 在每个从实例中设置非默认的 api username 与 api password，并确保在主仪表盘添加时使用相同凭证进行认证。
    - 步骤四：在主仪表盘上统一添加并标注实例
        - 在主机 UI 上使用 “Add new bot” 功能，输入每个实例的 URL、API 用户名/密码、并给出有意义的显示名（包含策略名、state currency、dry/live）。
        - 手动刷新以确保连接状态从红变绿，确认已成功接入。
    - 步骤五：日常监控与迭代流程
        - 使用主仪表盘做日常健康与绩效的“快照”监控：关注 Open Profit、Close Profit、Open/Allowed、Balance、Wins/Losses 等字段，快速识别异常或亮点。
        - 对识别到的问题或优点的实例，切换到该实例的详情页面做更深的日志、参数或历史订单审查，必要时在 dry run 中复现改动，再逐步推向 live。
    - 步骤六：治理与安全
        - 定期更换或维护 API 凭证，最小化权限并使用 HTTPS/SSL。不要在公开或不受信任网络上暴露未经保护的实例。
        - 对 live 实例施行更严格的变更审查流程与回滚计划，避免在市场波动时出现不可控损失。
- 结果导向：这个框架的目标是把“分布式实验”变成“一目了然的控制器”，把策略研发从分散的独立试错，变成可度量、可追溯与可复制的迭代流程。通过集中仪表盘做快速判别，再在单实例做深度动作，可以显著提升策略开发效率，缩短从发现到验证再到量化放量的周期。

# 总结

视频核心在于介绍 Freaktrade 新增的聚合仪表盘功能：通过部署一个主实例作为统一入口，并在每个策略实例的配置里允许该主实例的 API 访问（修改 cores origins 并设定 API 凭证），配合反向代理和 Docker 容器化部署，可把多个并行运行的 bots 汇聚在同一页面进行实时监控。作者演示了如何配置、如何在主仪表盘添加实例、命名约定与字段含义，并强调以 dry run 为主、凭证安全与命名规范的重要性。总体而言，这套做法能显著提升并行策略管理与快速迭代的效率。
