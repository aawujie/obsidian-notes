## 最核心的部分

### `chassis/simulator/` — 底盘仿真器核心

**为什么最核心**：它是整个 HIL 系统的「心脏」，所有其他模块都围绕它运转。

1. **`BaseVehicleSimulator`**（`base_simulator_class/`，1,261 行）定义了系统的「行为契约」—— 6 大接口族、30+ 个虚函数：

| 接口族 | 代表方法 | 用途 |
|---|---|---|
| A. 报文池操作 | `SetSignalValue()` / `GetSignalValue()` | CAN/FlexRay 信号读写 |
| B. 发送周期控制 | `UpdateMessageSendPeriod()` | 修改报文发送频率 |
| C. SECOC/校验/滚计 | `SetSecocEnabled()` / `SetChecksumEnabled()` | 安全通信控制 |
| D. 状态查询 | `GetChannelNames()` / `IsChannelRunning()` | 通道状态 |
| F. 握手信号 | `SetHandshakeSignalEnabled()` | ECU 握手控制 |
| G. 底盘启停 | `StopChassis()` / `StartChassis()` | 全局启停 |

2. **`business/`**（4,341 行）实现关键业务逻辑：
   - `vehicle_model_bridge/`：5 种动力学桥接处理器（P03/DE09/P177/A10 + 基类），连接仿真引擎与 CAN 信号
   - `handshake/`：ECU 握手协议实现
   - `vin/`：VIN 码唤醒管理（GWM 专有）
   - `wake_up/`：网络唤醒（GL 系列 NM 唤醒）
   - `hil_socket_bridge/`：GUI ↔ 底盘的 Socket 桥接

3. **三大系列工厂**（gl/ + gwm/ + lp/，共 ~4,600 行）通过配置化 JSON 创建对应车型仿真器

**核心地位体现**：
- GUI、for_local、for_remote、所有 server、pybind_so 最终都通过它与真实硬件交互
- 任何新车型适配首先要确保这层正确工作
- 底盘仿真器的行为直接决定域控是否能正确启动 ADAS 功能

## 最复杂难维护的部分

### 第一名：车型分支的散落硬编码

**不是某个具体模块，而是一种遍布整个仓库的结构性问题。**

从 B26A1 的适配实录可以看到：新增一个车型需要在 **20+ 处、15+ 个文件** 中手动添加 `if/else if` 或字符串。这些散落在：

| 散落位置                       | 文件数 | 典型形式                           |
| -------------------------- | --- | ------------------------------ |
| `src/server/sim-*/main.cc` | 5   | `car == "B26A1" \|\|`          |
| `src/gui/` 各处              | 6   | `kCarTypeMap`、`GwmCarSet`、条件分支 |
| `src/utility/`             | 2   | `CarType` 枚举、switch case       |
| `tools/`                   | 2   | Python 字典/if-elif              |
| `config/`                  | 2   | jsonnet 段、JSON 条目              |
| `pipeline/`                | 1   | shell case 分支                  |

**难维护原因**：
- **遗漏风险极高**：忘了改某个 `main.cc` → 该传感器不支持新车型，但编译不会报错
- **无编译期保障**：大多数是字符串比较，拼错不会报错
- **修改成本线性增长**：每新增一个车型，改动量相同
- **知识分散**：没有单一的「车型注册中心」，需要人工记住所有需要改的地方

> 改进方向：引入车型注册表（单一数据源），各模块从注册表读取配置，而非各自硬编码。

### 第二名：`chassis/vehicle/` — 255 万行车型数据

| 维度 | 复杂性 |
|---|---|
| 体量 | 6 个数据家族，134 个子目录，255 万行 |
| 来源 | 由外部 DBC 工具链从 `.dbc` 文件生成 |
| 格式 | JSON（报文定义）+ Python（枚举）+ JSON（CAN ID 映射） |
| 耦合 | CarplusConfig 通过硬编码路径或 DataFileManager 读取 |

**难维护原因**：
- DBC 变更后需要重新生成，生成工具链在 `vehicle/data_tools/` 下，分 GL/GWM/LP 三套
- 生成的文件极大（单个 `_messages.json` 可达数万行），diff 难以 review
- 多车型共用同一个 `vehicle_families` 数据目录，修改一处影响多个车型
- 没有自动化的一致性校验（如信号名是否在 DBC 和枚举文件中一致）

### 第三名：`chassis/strategy/` — 信号处理策略链（3,556 行）

| 策略 | 变体数 | 复杂性来源 |
|---|---|---|
| CRC8 | 5 种（base/payload/9byte/33byte/A10） | 每种对字节顺序、偏移、初始值、多项式不同 |
| Rolling Counter | 2 种（普通/Block） | 计数器位宽、溢出行为差异 |
| Timestamp | 3 种（UnixMs/Datetime/GlSplitUnix） | 拆分方式、精度、时区处理 |
| VIN | 1 种（GWM 专有） | 多帧 VIN 码分段注入 |

**难维护原因**：
- **必须与真实 ECU 的实现 bit 级一致**，否则底盘会拒绝报文（CRC 校验失败）
- CRC 多项式和初始值在不同车型间可能不同，但代码中通过策略组合来处理
- 策略链配置在 `strategy_chain_config.json` 中，配置错误会导致报文被 ECU 拒收，且错误表现不明显（仅超时报错）
- 缺乏单元测试覆盖（需要真实 CAN 数据对比验证）

### 第四名：`server/sim-lidar/`（4,540 行）

| 型号 | 协议 | 复杂性 |
|---|---|---|
| AT128 | 私有 UDP v4.3 | 需解析 dat 配置文件，构造多帧点云包 |
| ATX | 私有 UDP v4.3 + TCP 命令 | 双通道 + 命令响应 |
| EMX192 | 私有 UDP | 独立协议 + 故障注入 |
| MX | 私有 UDP | 独立协议 + 故障注入 |

**难维护原因**：
- 4 种激光雷达使用完全不同的二进制协议，无法抽象共用
- 协议细节来自厂商文档（可能不完整或有歧义）
- 需要将 ROS PointCloud2 标准格式逐字节转换为私有格式
- 支持频率异常注入（丢帧仿真），增加了状态管理复杂度

## 核心 vs 复杂度矩阵

```
                        低复杂度                高复杂度
                    ┌──────────────────┬──────────────────┐
                    │                  │                  │
         高核心性    │  for_local       │  chassis/        │
                    │  (763 行)        │  simulator       │
                    │  简单进程管理     │  + strategy      │
                    │                  │  + vehicle       │
                    ├──────────────────┼──────────────────┤
                    │                  │                  │
         低核心性    │  tools/          │  sim-lidar       │
                    │  (4,206 行)      │  (4,540 行)      │
                    │  独立工具脚本     │  4 型号私有协议   │
                    │                  │                  │
                    └──────────────────┴──────────────────┘
```

**最需要关注的象限**：右上角 — `chassis/simulator` + `strategy` + `vehicle`。它既是系统核心，又是最复杂的部分。

## 改进建议

| 问题 | 建议 | 优先级 |
|---|---|---|
| 车型硬编码散落 20+ 文件 | 引入车型注册表（单一数据源 JSON/YAML），各模块从注册表读取 | 🔴 高 |
| DBC 数据 255 万行无校验 | 添加 CI 一致性检查（枚举 ↔ CAN ID ↔ messages 交叉校验） | 🟡 中 |
| strategy 缺乏单测 | 添加基于真实 CAN 数据的 CRC/RC/Timestamp 策略单元测试 | 🟡 中 |
| sim-lidar 4 种协议无抽象 | 提取公共接口层（PointCloud → Binary 转换器抽象） | 🟢 低 |
| server/sim-* 的 main.cc 车型分支 | 改为配置驱动（从注册表读取传感器参数），消除 if/else 链 | 🔴 高 |
