# 1. Metadata

- Title: 從 Solana 到 Sui：一個 DeFi 團隊的遷移與觀察
- Author: Kyrie（訪談者口述整理）

# 2. Overview

這段對話核心在描述一支原本在 Solana 生態開發選擇權交易所的 DeFi 團隊，為何決定把早期開發重心由 Solana 轉到 Sui，以及兩個生態在開發語言、資安防護、共識機制、穩定性與驗證節點（validators）設計等面的差異觀察。結論是：團隊基於技術需求（運算速度與防呆）、開發成本、商業時機（先行者優勢）與對未來去中心化與穩定性的期待，選擇在 Sui 做早期開發；同時認為 Solana 仍有工程師與項目根基，只是目前處於低迷期。

# 3. 按照主题来梳理

## 3.1 背景與遷移決策過程

- 團隊起始背景：這個團隊在 2021 年正式開始做項目，核心產品是一個在鏈上做選擇權（選擇權是金融衍生品的一種，允許買方在未來以特定價格買入或賣出標的資產）的交易所。因為選擇權涉及複雜且大量運算，因此對底層鏈的運算性能、延遲與交易處理能 力有較高要求。起初選擇了 Solana，主要原因是其性能能滿足項目的基礎需求。團隊在 Solana 做了數月開發，並參與 Solana 的 hackathon（駭客松），在 DeFi 組別獲得名次，並因此與 Solana Foundation 及相關官方項目建立合作關係，獲得一定的資源與曝光。
- 生態環境與外部事件影響：在團隊發展期間，加密市場遭遇 Luna（Terra）崩盤與 FTX 爆雷等事件，整體市場氣氛低迷，Solana 生態受到衝擊。Solana 在遭遇這些事件後「一蹶不振」，造成生態活力與資金流動變化，團隊開始思考替代方案與長期路徑。
- 為何看上 Sui：在進行多方研究後，團隊認為 Sui 在技術層面符合其需求（運算性能、防呆與資產模型），且 Sui 作為新興公鏈存在先行者優勢（早期進入可以取得更高的資源、使用者與市場機會）。團隊也正好有新產品構想，適合在新鏈上嘗試早期開發。綜合技術、商業時機與轉換成本的考量後，決定把早期開發投入 Sui 上。
- 技術人力與語言轉換影響：團隊在 Solana 上使用 Rust，而 Sui 使用 Move（基於 Rust 發展、針對加密資產設計的語言）。由於 Move 與 Rust 在語法或概念上有相似性，原本的 Rust 工程師只花兩到三週就能掌握在 Move 生態下的開發要領，這降低了遷移的技術門檻。Move 設計針對資產特性做了許多內建限制與保護，能讓開發者更快上手並減少錯誤，這也是團隊願意轉移的因素之一。
- 商業與時機層面的考量：團隊認為 Sui 當時處於早期階段，具有更大的創業與行銷機會（先行者紅利），相較於在 Solana 已高度競爭且受外部事件影響的環境，Sui 提供了更合適的切入時機。團隊也注意到轉換成本（例如重新審計、代碼重寫等）在可控範圍內，因此決定嘗試。

## 3.2 Move（Sui）與 Rust（Solana）在開發與安全性的差異

- 語言定位與設計初衷：Rust 在 Solana 生態被廣泛使用，靈活性與表現力高，但不是專門為數位資產設計；Move 是為了加密資產特性特別設計的語言（Move 為一種基於 Rust 的資產導向語言），其語言特性帶有防呆（safety-by-design）機制，強制遵守一些資產相關的約束，降低合約中出現不當資產操作的風險。
- 開發成本與審計影響：在 Solana（Rust）上，開發者常需要撰寫大量額外代碼來處理帳戶（account）類型的判別與邊界情況檢查，這些驗證性代碼會增加代碼長度（受訪者估計約多出 30–40% 的代碼量），導致開發與審計成本上升（審計機構通常依代碼行數或複雜度報價）。相對地，Move 的語言限制與協議標準減少了需要寫的驗證邏輯與邊界檢查，降低錯誤率與審計負擔。
- 資產行為的可預測性：Move 的資產模型限制了資產可以做或不可以做的操作，例如禁止任意複製或丟棄資產（prevent arbitrary duplication/disposal），使得某些資產的供給規則或轉移行為在語言層面更容易被保護與保證。相比之下，使用 Solidity 或 Rust 的智能合約允許開發者寫入高度自定義的邏輯，若開發者惡意或失誤，可能產生像「交易觸發時會創造額外代幣」這類不直觀或有害的行為。一般使用者難以閱讀合約代碼來驗證這些細節，因此 Move 的標準化協議與限制能提高對一般用戶的安全保障與信任。
- 使用者角度的影響：對於非技術使用者，Move 的好處在於降低理解與信任成本。若項目遵循官方或標準協議，使用者不需要一行一行審查代碼，就可以對「Transfer」等基本行為有較高的信任，降低被奇怪邏輯欺騙的風險。總結來說，Move 在語言層面引入的防呆與資產約束，是提升使用者安全性與整體生態信任的重要因素。

## 3.3 Sui 的共識與資源分流機制（穩定性與吞吐）

- 物件（object）模型與分流概念：Sui 在底層對資產做了明確分類，將鏈上資產分為「自有物件」（owned objects）與「共享物件」（shared objects）兩大類。自有物件指的是只有單一帳戶擁有控制權的物件，例如單純從 A 帳戶轉移到 B 帳戶的情形，操作相對簡單；共享物件則是多方可以共同調用或改變的物件，例如 DeFi 的流動性池（liquidity pool）或其他多人共同互動的資產。
- 不同共識路徑以降低資源競爭：針對自有物件與共享物件，Sui 採用不同的共識機制或處理路徑，使得對自有物件的操作能夠走更輕量且並行化的通道，而共享物件則使用更慎重且需要協調的機制。這種分流（簡單比喻為餐廳內用與外帶分流）能在高交易壓力時減少整條鏈的資源競爭情況，避免單一類型的高頻交易（例如 NFT minting 大量交易併發）導致整個網路資源被擠壓、其他交易無法處理或鏈上停擺的問題。
- 與 Solana 的差異與優勢：在 Solana 上，鏈上的運算資源是較為共享的，當有大量併發交易或某些活動爆發時（例如熱門 NFT mint），整個網路可能被擠壓，造成其他應用被「卡住」或系統負荷過重。Sui 的分流機制試圖把這類影響局部化，讓大量自有物件的操作能在不影響整體網路運作的情況下被快速處理，從而提升整體穩定性與用戶體驗。
- 穩定性對用戶與開發者的意義：對一般使用者、尤其是對 DeFi 或高頻交易應用來說，穩定性意味著更少的交易失敗、更低的延遲與更可靠的服務。對開發者而言，分流機制減少了因為其他應用高併發而導致的不可預見性問題，使得應用在上線與運營期間更穩定、風險更低。由於 Sui 在底層語言與共識設計上把資產屬性納入考量，這種穩定性的提升被視為 Sui 對比其他鏈的一項重要技術優勢（亦指出 Aptos 沒有相同的分流機制；出處基於受訪者觀察）。

## 3.4 驗證節點（validators）經濟與去中心化考量

- 驗證節點數量與去中心化並非等同：在判斷一條鏈的去中心化程度時，驗證節點的數量是一個重要指標，但僅看數量並不充分。若大量節點地理與實際控制權集中（例如多數節點都在單一區域或由相互認識的團體運營），那麼表面上的「多節點」並不代表真正的分散權力或容易引入新參與者。
- Solana 的現狀與問題：受訪者指出 Solana 當前仍有大約數千個節點，但這些節點多數是早期參與者或機構，且門檻相對較高（例如需要質押一定數量的代幣），使得新節點或普通人較難加入，節點的流動性與替換率有限。早期參與者在低成本取得大量代幣，導致後期吸引新進者意願降低，進一步影響去中心化的動態性與民主性。
- Sui 的設計在驗證節點引入面向：Sui 在代幣經濟（tokenomics）設計上考慮到如何降低成為驗證節點的門檻，並透過補貼或其他機制鼓勵新節點加入，讓驗證節點的進入成本不會過高，從而提高節點的流通性與汰換率。這樣的設計有助於維持一個更健康的去中心化治理結構，使得節點分佈不會長期被少數早期者壟斷。
- 實務意義與觀察：團隊認為 Sui 在驗證節點的經濟設計上，是一項關鍵策略，旨在確保生態長期能吸引新的驗證者，並保持治理與網路安全的動態健康。這一點雖然在短期看不見立即效果，但對於一個要長期運作並希望維持去中心化承諾的公鏈來說，這類設計被視為前瞻且必要的。Solana 若能度過當前低潮，仍有許多工程師與成功案例，但其節點結構的可替換性與包容性則是需要關注的問題。

## 3.5 對兩個生態未來發展性的看法與團隊策略

- Sui 的發展定位與期望：從開發者角度，Sui 被視為仍處在早期階段的一個生態，很多技術與經濟機制都在逐步建立與調整中。這代表 Sui 有機會解決過去在 EVM 生態或 Solana 遇到的一些問題（例如資產模型、防呆、安全性、資源分流與驗證節點設計），但同時也需要時間來累積使用者、驗證機制與實際運營經驗。團隊建議對 Sui 保持耐心，不必過度 FOMO（害怕錯過），而是觀察其逐步成熟的過程。
- Solana 的定位與持續性：Solana 目前處於較低迷的階段，但並非完全衰亡。Solana 早期吸引了大量來自矽谷的優秀工程師（許多來自 Google、Facebook 等具有 Rust 經驗的人），這些技術人力資源與早期的成功案例，讓 Solana 在技術蓄積與項目品質上仍具實力。若 Solana 能夠渡過市場低潮，保有開發者社群並解決既有痛點，仍有機會復甦。
- 團隊策略與雙生態觀察：團隊之所以移往 Sui，一方面是基於先行者的機會、語言（Move）的安全訴求與 Sui 的共識分流設計；另一方面，團隊也不排除持續關注甚至在 Solana 與其他生態間合作或保留關係，因為 Solana 的工程師社群與既有項目基礎依然存在價值。總體而言，團隊採取的是多元觀察與資源分配策略：在 Sui 上做早期開發以取得技術與市場先機，同時對 Solana 的動向保持關注，評估未來可能的協作或回流機會。

# 4. 框架 & 心智模型（Framework & Mindset）

- 決策框架：選擇區塊鏈生態的多維評估
    - 需求導向優先：首先從產品的技術需求出發（例如高運算量、複雜合約邏輯、延遲敏感性），評估哪些鏈能夠滿足這些基礎條件。團隊案例中，選擇 Solana 起因是其能滿足選擇權交易所對運算與延遲的需求；後來選擇 Sui 則是基於語言特性與資產模型更貼合的判斷。
    - 技術轉換成本評估：評估現有工程師技能（如 Rust）能否順利轉換到目標鏈的語言（如 Move），以及轉換所需的時間與風險。團隊發現 Rust 工程師能在約兩到三週掌握 Move 的主要開發概念，使遷移成本在可接受範圍內。
    - 商業時機與先行者優勢：衡量新鏈的市場時機（是否為早期可取得先行紅利）以及產品能否從早期部署中獲益。若鏈處於早期且技術符合需求，早進場可能帶來使用者與資源的溢價機會。
    - 安全與審計成本：比較在不同語言與生態下的審計負擔（代碼長度、邊界情況檢查等），以量化成本差異。Move 的防呆設計被視為能減少審計工作量與降低錯誤風險，這成為重要評估指標。
    - 生態與治理可持續性：檢視驗證節點結構、代幣經濟是否支持長期去中心化與節點汰換，以及社群/工程師能否長期支持生態；避免只看短期熱度而忽視長期治理風險。
    - 綜合決策機制：將上述要素綜合權重化（技術需求、開發成本、商業時機、安全性、長期可持續性），作為最終選擇鏈或分配資源的依據。
- 開發者心智模型：安全優先與用戶信任導向
    - 防呆與資產模型優先：在開發金融或資產相關的應用時，優先選擇語言與平台能在語言層面提供資產保障（如禁止任意複製、不可丟棄），讓安全性成為第一道防線，而非僅依靠事後審計或社區監督。
    - 最小化自定義危險行為：盡量採用已被驗證的標準協議或官方提供的實作，避免過度自定義基礎行為（例如 Transfer）以減少潛在的不當邏輯導致資產風險。這使得非技術使用者也能基於協議標準對合約行為建立基本信任。
    - 開發效率與審計成本並重：在語言選擇與架構設計上，考量到會影響審計成本的因素（代碼複雜度、邊界檢查數量），在早期就優化實作以降低後期審計與維運負擔。
    - 長期生態留意：除了短期技術優勢，開發者需關注生態的治理、節點多樣性與代幣經濟是否支持新節點加入，因為這些會影響系統的長期安全與去中心化。
    - 保持彈性：在跨鏈或多鏈時代，保持技術與商業策略的彈性，必要時能在多個生態間分配資源或遷移，降低對單一鏈的依賴風險。

# 总结

這段對話呈現一個實務上的、以產品需求與生態判斷為核心的鏈遷移案例。關鍵原因包括 Move 語言在資產保護上的防呆機制、Sui 底層的資源分流與共識設計、以及代幣經濟對驗證節點進入成本的考量。團隊選擇 Sui 是綜合了技術匹配、開發遷移成本與商業時機（先行者優勢），而對 Solana 則保持尊重與持續關注，認為其工程師資源與既有項目基礎仍有價值。整體心智模型建議以需求驅動、風險控制、以及長期生態可持續性做為決策基礎。
