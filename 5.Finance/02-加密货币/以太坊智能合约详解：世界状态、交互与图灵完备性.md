# 3. 按照主题来梳理

## 3.1 世界状态（World State）与账户对象

- 世界状态是以太坊系统的核心数据层，所有链上状态变化最终反映为世界状态的改变。世界状态本质上是大量账户（objects）的集合，这些账户分成两类：普通账户（Externally Owned Accounts，EOA）和合约账户（Contract Accounts）。每个账户都由一个地址（address）标识，并保存一些基本字段：nonce（防重放计数器）、balance（余额）。合约账户在此之外还包含 code（合约运行时代码）和 storage（持久存储）。
- 普通账户非常简单：地址→nonce、balance（两个数字）。合约账户除了这两项外，还拥有 code（字节码）与 storage（按 256-bit（比特）为单位组织）。视频用颜色和格子直观表述这些字段的位宽：例如地址通常为 160 位（20 字节，视频用 80 个双色格子模拟每格 2 位），nonce 在示例中以 64 位表示，balance 为 256 位（EVM 内部以 wei 的整数计量），合约的 storage 按 256-bit 单元划分（每个存槽存 256 bits）。
- 世界状态并非静态的文件；它通过区块链共识（例如视频提及的 proof-of-stake、Merkle 树、区块哈希等机制）在新区块被打包时被维护与变更。但核心观点是：以太坊的所有复杂底层机制，仅仅是为了维持并按规则更新这个“世界状态”。当交易执行完成，唯一的外在可见结果就是世界状态中某些账户的字段（如存储槽、余额、nonce）发生了变化。
- 账户地址来源与控制机制上存在根本差异：EOA 的地址与私钥直接相关（从私钥派生公钥，再哈希取末 20 字节得到地址），这使得我们能够用签名验证交易是否由该私钥持有者发起；合约地址则是部署计算出来的标识（常见是部署者地址 + 部署时的 nonce 的哈希取末 20 字节，或 CREATE2 用 sender + salt + codehash 的哈希取末 20 字节），合约没有私钥，其行为由合约代码决定，因此地址更像是一个标识符而非“受私钥控制”的账户。
- 余额（balance）在链上以最小单位 wei 表示，所有内部计算、转账与余额记录都以整数 wei 进行，不以小数处理。比如用户界面显示的 ETH（ether）是把 wei 除以 10^18 后的可读表示，但链上永远以 wei 记账。这避免了小数误差与分割问题，也是链上价值转移的基础单位。

## 3.2 合约字节码（Bytecode）、存储（Storage）与构造流程（Constructor / Initialization）

- 合约的“逻辑”以字节码（EVM bytecode）形式存储在世界状态中。字节码是由高阶语言（例如 Solidity）编译而来的一系列 EVM 操作码（opcodes），每个操作码以一个字节表示，复杂操作可能后跟若干字节作为参数。视频提醒我们，在链上看到的只是十六进制字节序列（每两个十六进制字符代表一个字节），而这些字节由 EVM 在执行时解释为各种操作，如 PUSH、CALL、SSTORE、SLOAD、JUMP 等。
- 合约部署时涉及两类代码：创建时的合约创建代码（creation code）和之后存储在链上、供调用时执行的运行时代码（runtime code）。创建代码除了包含运行时代码本身，还包含初始化逻辑：例如构造函数（constructor）的调用、初始 storage 的分配与设置等。创建执行完成后，EVM 会把运行时代码放入合约账户的 code 字段，并将创建时的临时状态清理，最终世界状态中保留的是运行时代码和初始化后的 storage 状态。
- Storage 在 EVM 中抽象为一个巨大的稀疏键值存储（key-value store），每个键和值是 256 位宽。固定位（固定数量的变量）在部署时就对应好某些固定存槽，但映射（mapping）和动态数组等数据结构会通过哈希等方式动态计算存储位置，从而支持运行时扩展的内容。视频强调：变量的“类型结构”在部署后就被固化（你不能在链上随意给合约加新变量），但映射/数组里的条目数量与具体值是可变的。
- 构造函数与部署流程的要点：开发者上传的并非最终运行时代码的纯净拷贝，而是创建代码。创建代码执行包括调用构造函数、初始化变量、设置 storage 初值、决定并写入运行时代码，然后创建交易结束后，运行时代码驻留在链上。部署时决定的存储“结构”与变量集合在合约生命周期内不可随意扩张（除非合约设计了代理/可升级模式），因此设计和部署时需要考虑未来兼容性与扩展性。

## 3.3 合约交互：交易、calldata、函数选择器（Function Selector）与 ABI（Application Binary Interface）

- 与合约交互的基本方式是发送交易（transaction）到合约地址。交易可以改变世界状态（会产生 gas 消耗），也可以是只读调用（eth_call）。交易内部携带的核心一项就是 calldata（调用数据），calldata 是一个字节数组，告诉合约要调用哪个函数并传递哪些参数。常见的 calldata 编码遵循 Solidity 的 ABI 编码规范：函数的前 4 字节是函数选择器（function selector），后续按 32 字节（256-bit）对齐打包的参数构成。
- 函数选择器的生成方式：取函数签名（function signature），即 "functionName(type1,type2,...)" ——注意是函数名加参数类型，不包括参数名；对该签名做 keccak256 哈希（Keccak-256），然后取哈希的前 4 字节（即前 8 个十六进制字符）作为函数选择器。该选择器填在 calldata 的最前面，用以在合约内部区分不同的 public/external 函数。
- 一个重要澄清：EVM 并不知道“函数选择器”这一概念是语义化的。EVM 只是按顺序读取并执行合约字节码。函数选择器的解析逻辑并不是 EVM 的内置路由；相反，编译器在生成合约运行时代码时，会把“读取 calldata 的前四字节并比较到某个分支，匹配后跳转到对应函数字节码”的逻辑写入字节码。换言之，函数选择器的“路由表”是以字节码形式存在于合约内部，由合约自实现。编译器可以为这种比较逻辑生成不同实现：线性串行比较、二分查找或更复杂的跳转表，以在 gas 成本与字节码大小间做权衡。
- ABI（Application Binary Interface）是编译器生成的描述性接口，向外界（钱包、前端、用户）说明合约的哪些函数是 public/external、参数类型、返回类型等。ABI 方便外部工具构造正确格式的 calldata，解析返回数据。ABI 本身只是一个方便的“约定”或“契约”，并不强制 EVM 做什么，它只是帮助人类或工具知道如何与合约交互。
- 可见性（visibility）与修饰符（modifiers）：Solidity 提供的 public、private、external、internal 等修饰符也并非 EVM 原生特性，而是影响编译器如何组织字节码以允许或禁止某些外部入口。private 或 internal 语义在字节码层面通过不生成对外可达的入口路径来实现。Modifiers（修饰器）在编译时会被展开或以字节码形式插入到函数逻辑中，从而在调用前后执行检查（例如 onlyOwner）或更改行为（例如 payable 允许接受 ether）。Payable 标注允许函数在调用时同时接收以太（ETH）；如果函数非 payable 而交易包含 value，通常会导致执行 revert。
- 交易回执（transaction receipts）与事件（events）：当交易执行完成，EVM 会返回交易回执，其中记录了执行结果、gas 用量、logs（事件）等信息。事件（通过 EVM 的 LOG* opcodes 实现）是链上轻量级输出，用于客户端快速查看某些事情是否发生（例如 ERC-20 Transfer 事件）。事件与世界状态不同：它们存在于交易回执 / 日志树中，方便监听并重构应用逻辑，而不用每次都去解析世界状态的变化。

## 3.4 关于视频图示的解读：合约“被唤醒”的隐喻与函数/存储的可见性

- 视频用大量图形化元素来传达合约的抽象结构：把合约当作静态数据（代码与存储）在世界状态中以“平板”的形式存在，只有当交易触发时，EVM 像一架“飞行器”飞来，把合约“唤醒”，将字节码转为执行的“机器”，驱动其内部的机器齿轮去处理 calldata、读写存储并最终导致状态变更。这个隐喻突出两个事实：合约在链上本身只是静态数据（字节序列与存槽），而“执行”是由外部事务（带签名与 gas）使 EVM 启动并顺序运行这些字节码，从而影响状态。
- 在图示中，public 函数通常标记有函数选择器的标签，并在合约“表面”可被 EVM 直接匹配与调用；private 函数则“隐藏”在内部，不会被外部 calldata 的前四字节路由到。这表达了可见性在语义上的效果：即便合约的字节码可以被反编译、分析并看到私有逻辑，外部调用路径并不存在，调用者无法直接触发那些私有入口（除非通过合约内的其他公开函数间接触发）。
- 视频用“引脚/接口栅格”表示函数参数的占位与 256-bit 对齐的 ABI 打包；用“显示屏”表示函数的返回值；用“以太水晶”表示 payable 的 value 流入合约余额；用导线连接到存储区表示某些函数会读/写存储（view 函数仅读并返回，不修改；pure 函数既不读也不写存储，仅依赖输入做计算）。这些视觉元素帮助理解 EVM 执行时的实际数据流动：calldata → 字节码解析（选择函数）→ 在堆栈/内存/存储间操作 → 可能修改 storage 与 balance → 产生 logs/事件与返回值。
- 最后，图示强调“执行的后果”回归到世界状态的变化：无论合约内部做了多复杂的计算，链上最终可见的仍是一些存储槽的改变、账户余额转移、以及可能的事件记录。执行的“动画化”只是帮助理解那些本来静态的数据在被程序运行时如何被引用与修改。

## 3.5 图灵完备性（Turing Completeness）的含义与影响

- 什么是图灵机（Turing Machine）与图灵完备（Turing completeness）？图灵机是 1936 年由 Alan Turing 提出的抽象计算模型：极长（理论上无限）的带（tape）和一个读写头（head），根据状态转移表读取/写入符号并移动。图灵证明该模型在计算能力上是通用的：所有可计算的问题，只要在原则上是可计算的，图灵机就可以计算出来（除不可判定问题诸如停机问题外）。图灵完备性表示某一计算模型具备图灵机的表达能力，即它可以计算任何可计算函数（在资源与时间允许的前提下）。
- 以太坊智能合约具备图灵完备性：EVM 的指令集与内存/堆栈模型能表达任意复杂的算法。意味着在理论上，没有计算“种类”是合约做不到的（仍受时间与 gas 限制以及可用存储限制）。图灵完备带来的关键属性是通用性（generality）：一种通用的、可编程的全球计算环境，从货币/代币、交易自动化到更复杂的自治组织、市场与协定，都可以在其上实现。
- 需要区分“表达能力（expressiveness）”与“性能/资源”。图灵完备并不意味着合约在现实中可以无限快或无限记忆；物理实现总有边界（gas、区块 gas 限额、存储费用）。图灵完备性讲的是“可以用程序表达任何可计算的问题”，而不是“可以在任意资源约束下完成”。例如 GPU、量子计算机并不是更“有表现力”的机器——它们在某些任务上更快或更好并行化，但在可计算性层次上依然被图灵机涵盖。
- 图灵完备性的深远影响在于它赋予以太坊成为“世界计算机”（world computer）的潜力。历史上对通用计算能力的低估常源于人们只看到短期内的具体应用（早期电脑的游戏、文本处理；早期互联网只是电子邮件或简单页面）。但一旦拥有通用机器与广泛连接（网络），新的组合与创新呈指数级爆发：同理，链上通用计算加上共有状态与抗审查、确定性执行的特性，可能催生当前难以完全预见的全新系统（如链上治理/DAO 的新范式、去中心化金融的进一步抽象、甚至更上层的组织与治理结构）。
- 因此视频提醒读者：评价以太坊或类似系统时，不要仅凭现有应用去判断其潜力；相反应认识到“通用性”与“全局共享计算/状态”的长期影响。正因为合约是图灵完备且运行在一个全网共享且不可篡改的世界状态之上，它为将来可能出现的跨领域、跨组织、甚至制度层面的重构提供了技术基础。这个角度才是理解“世界计算机”重要性的关键之一。

# 4. 框架 & 心智模型（Framework & Mindset）

- 世界状态中心化思路（World State-Centric Model）：将以太坊的设计与开发心智模型放在“世界状态”上，而不是把合约当成独立的服务器端程序。具体步骤与要点：
    1. 把世界状态视为系统的单一事实来源（single source of truth）：所有合约与账户的数据、余额、nonce 都存于世界状态，执行的目的是修改这一状态。理解一个操作的最终影响即是理解它如何改变世界状态中的哪些存槽或余额。
    2. 设计合约逻辑时先定义世界状态的结构：明确哪些字段必须长期存在、哪些值需要可变、哪些需要被外部验证或审计。在部署时这些结构（固定变量数量与映射的存在）会被固定下来，慎重设计以避免后悔成本。
    3. 以最小状态变更与确定性为原则：任何交易都需要支付 gas，以太坊鼓励合约尽可能在有限状态改动下完成目标。将状态变化降到必要的最小集可以节约成本并降低复杂性。
    4. 把事件（logs）用作外部观察与索引机制：不要试图通过过多的世界状态变更做通知，合理使用 events 将交易的关键信息写入日志，这便于客户端解析与响应，且相对便宜。
    5. 想像执行为“唤醒”动作：只有交易到达时字节码被实际执行，因此测试、审计和组合逻辑应考虑合约可能在不同输入顺序与并发环境（同区块的交易顺序）下的行为。
- 接口与实现分离（ABI 与字节码实现模型）：这是一个工程心态，强调外部可用契约（接口）与内部实现（字节码）之间的职责划分。
    1. 在设计合约时明确 ABI：哪些函数是 public/external，参数类型如何，哪些事件会被发出。把 ABI 当作对外服务契约，单一可读的 ABI 有利于钱包、前端与审计。
    2. 理解 EVM 不认识高级语义：函数选择器与可见性语义由编译器/字节码实现，所以你不能假设 EVM 会自动保护“私有”逻辑。验证、审计时要检查字节码是否确实没有对外入口。
    3. 性能与字节码大小权衡：编译器会在生成函数路由逻辑时权衡 gas（运行时成本）与字节码大小（部署成本）。当函数数量巨大时，合理划分模块、合约拆分与使用升级代理可以减少单合约复杂度与 gas 开销。
    4. calldata/ABI 编码理解：前端与工具链必须严格遵守 ABI 编码（函数选择器 + 32 字节对齐的参数），测试中模拟真实 calldata 与异常输入可以避免运行时错误。
- 通用性与长期思考（Generality & Long-term Perspective）：
    1. 把合约平台视作“通用机器”而非仅仅是“货币/代币脚手架”。图灵完备+共享状态的组合创造了无法简单类比的潜在应用空间。
    2. 避免以当前可见的应用范围去限定平台未来价值。历史经验（早期计算机、互联网）表明通用性往往在最初阶段被低估。
    3. 设计合约与组织时要考虑可演化性：虽然部署后合约结构难以改变，但可通过代理模式、模块化设计、兼容性接口等方式为将来调整留出空间。
    4. 风险管理和治理：通用性也带来滥用风险与复杂性，所以在追求通用能力的同时同步构建治理、审计与升级策略，考虑到合约不可更改性与经济后果。
- 这些心智模型并非只是理论性的抽象，而是直接影响到合约的架构决策、测试策略、部署成本估算、以及长期维护与升级路径。把这些框架内化，可以帮助工程师从概率上降低灾难性错误、提高系统演化能力，并更好地评估以太坊生态的长期价值。

# 总结

视频系统地把以太坊智能合约放回“世界状态”这个核心语境来解释，从账户模型、地址来源、余额以 wei 的表达、合约字节码与存储结构，到交易/ calldata、函数选择器与 ABI 的关系，最后阐述图灵完备性带来的战略性意义。几个要点：合约在世界状态中是静态数据，只有在交易触发下 EVM 才执行字节码；函数选择器与函数路由逻辑由编译器写入字节码而非 EVM 内建；合约是图灵完备的，从而赋予以太坊成为“世界计算机”的潜力，但现实受限于 gas 与资源。理解这些概念有助于从工程与战略双重视角看待智能合约的设计、部署与未来可能性。
