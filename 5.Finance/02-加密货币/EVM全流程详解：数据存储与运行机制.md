## 3.2 EVM 中可存储数据的六个地方（总体架构）

- 视频首先列出 EVM 中数据可能存放的六个区域：stack（栈）、memory（内存）、calldata（调用数据）、storage（合约存储）、code（合约代码）、logs（日志/事件）。随后作者承诺本次讲解将重点深入前四项（stack、memory、calldata、storage），并简要提及 code 与 logs 的角色。
- 概念与区分：
    - stack（栈）：EVM 的操作栈，基于后进先出（LIFO）。每个栈项是一个 32 字节（256 位）字（word）。push、pop、swap 等 opcode 操作栈顶数据。栈用于短期、局部的算术、比较与传递值。
    - memory（内存）：临时、可变且按需扩展的线性字节数组，按 32 字节对齐的“字”进行读写（通过 MSTORE、MLOAD 等 opcode）。内存仅在交易/调用执行期间存在，交易结束后清空。Solidity 在内部会使用内存来构建复杂数据结构（如动态数组、临时缓冲区）。
    - calldata（调用数据）：调用合约时外部传入的一段只读字节序列（bytes），包含函数选择器及参数编码。calldata 不能被写入，因其只读特性读取成本更低（在合约设计中，经常建议尽可能直接读取 calldata，而不要把其内容复制到 memory 并修改，以节省 gas）。
    - storage（存储）：合约在链上的持久化存储。每个合约地址有自己的 storage，它由 32 字节的 slots（槽）组成，键和值均占一个字（例如 storage slot 的 key 是 256 位整数）。storage 的读写代价是最高的，但它是唯一在交易后仍然保留数据的区域（持久化到链上状态）。作者还指出底层的状态和 storage 的索引是以 Patricia Merkle Trie（帕特里夏-默克尔树）形式组织，但视频不会深入该实现细节。
    - code（代码）：合约的字节码存放在合约帐号的 code 字段中，这也是可以被读取的（例如 address.code），并在执行时被解释为 opcode 序列。代码本身可以被视为“只读存储”。
    - logs（日志）：事件的记录在交易中作为 logs 发出，不能被 EVM 合约在运行时读取（对合约而言 logs 是写入一次后对执行上下文只读／外部可查）。logs 常用于事件追踪与索引。
- 重点对比与实践建议：
    - 临时 vs 持久：stack、memory、calldata 都是临时、交易生命周期内有效；storage 是持久化到区块链的。
    - 读写成本：calldata 读取通常最便宜（因为不用复制到内存），memory 在扩展时会带来 gas 增长（内存扩展代价呈非线性增加），storage 写入最昂贵（并有额外的长期状态变更成本）。这决定了在合约设计时应尽量把只读参数保留在 calldata，避免不必要的 storage 写入与 memory 扩展。
    - 数据单位统一性：stack 与 memory 与 storage 都以 32 字节 word 为基本单位，但使用模式不同（stack 是 push/pop，memory 是按地址写入/读取，storage 是通过槽 key 进行持久化）。
- 视频通过一个高层类比（想象一个机器人和四个放东西的位置）来说明这些存储区各自的职责：把数据交给机器人并指令如何操作，opcode 就是这些指令。此部分为理解后续 opcode 与执行流程奠定了概念基础。
- 小结：了解这六个区域的区分、生命周期与成本是理解 EVM 行为的第一步，也是后续分析 opcode、字节码和 gas 优化的前提。视频在此处给出了明确的实践建议：如“如果可能，尽量直接读取 calldata，不要复制进 memory 并修改”。

## 3.3 Stack 与 Memory 的细节与内存布局（含 free memory pointer）

- Stack（栈）的细节：
    - Stack 存储 32 字节（256 位）的 words。任何 push 操作都会把一个 32 字节的值放到栈顶，pop 则拿走栈顶的值。常见要放入栈的值包括 uint、bool、address、或指向 memory/storage 的指针（以 32 字节形式表示）。
    - 当 push 比如数字 1 时，该值在栈上的表示为 31 个 0 字节加上最后一字节为 0x01（共 32 字节）。这与 EVM 固定字长的设计有关，也是 opcode 在处理算术与逻辑运算时的基础。
    - Stack 的前几个元素通常直接被 opcode（如 ADD、CALLDATALOAD、MSTORE 等）所操作，因此写字节码或阅读反编译结果时，需时刻跟踪栈的内容与顺序。
- Memory（内存）的细节与布局：
    - Memory 也是以 32 字节 word 为单位进行读写，但不同于栈的是它不是 LIFO，而是通过明确的偏移（offset）进行读写操作（MSTORE、MLOAD、MSTORE8 等）。
    - Solidity 在内存中保留了特定的地址/word 作为“工作区”（scratch space）。视频指出内存的前几个 word 布局为：
        - 0x00（内存第一个 word）：保留（多为 0）。
        - 0x20（第二个 word）：保留（多为 0）。
        - 0x40（第三个 word）：存放 free memory pointer（自由内存指针）。
        - 0x60（第四个 word）：被保留为动态数组的初始空值位置（初始为 0），通常不会被写入。
        - 0x80（之后的首个可用位置）：实际第一个可写的自由内存位置，free memory pointer 初始值为 0x80。
    - free memory pointer 的作用：它指向内存中当前第一个未被分配的安全写入位置。Solidity 的运行时/编译器会在需要分配新内存时读取这个指针并将其更新，从而保证不会覆盖已分配的数据。将 free memory pointer 放在 0x40 并指向 0x80 的原因是为了简化初始化与减少需要显式加载的 word 数，从而轻微优化燃料（gas）开销。
    - 关于 0x60 的特殊保留：0x60 处被保留为动态数组（dynamic array）初始值（空数组的初始占位为 0），因此 free memory pointer 跳过 0x60 指向 0x80，以避免覆盖该保留。
    - 内存扩展的成本：当合约通过 MSTORE 写入远大于当前已分配位置的偏移时，会触发多次内存扩展操作。内存扩展的 gas 成本并非线性增长，而会随着扩展长度成增长（呈非线性，视频用词“成指数增加”来提示其高额成本）。因此在合约设计时应尽量避免写入高度稀疏的大偏移，或在可能的情况下对 memory 地址与大小进行合理管理，避免不必要的扩容。
- 交互模式与实践建议：
    - 何时使用 memory：当需要临时可变的、复杂的数据结构（如构造返回数据、拼接参数、处理内部变更）时使用 memory。但是如果只是读取外部传入的参数且无需更改，优先使用 calldata。
    - 指针与引用：在堆栈或内存中传递数据时经常使用指针（即 32 字节的偏移），这要求开发者理解如何在不同区域之间传递引用（比如把 calldata 中的偏移复制到 memory 以便 MLOAD），并明白复制本身带来的 gas 成本。
    - 读写成本权衡：stack 操作通常是廉价且直接的（在一个执行帧内），memory 读写需要考虑扩展成本，storage 写入是最昂贵且会持久化。因此高效的合约设计会尽量把短期、只读数据放在 calldata 和 stack，把临时可变数据放在内存，尽量避免不必要的 storage 写入。
- 小结：详细理解 stack 与 memory 的 32 字节单位、memory 的默认保留布局（0x40 存 free memory pointer、0x60 保留、0x80 初始可写）以及内存扩展的高成本，对于在 EVM 层面写出既安全又高效的合约至关重要。

## 3.4 Calldata 与 Storage 的特征与成本（含实践建议）

- Calldata 的性质与优点：
    - Calldata（调用数据）是外部调用（或事务）的输入字节序列，包含函数选择器（function selector）和参数 ABI 编码。Calldata 是只读的：EVM 不允许在运行时将 calldata 作为写目标，因此它不会被复制回链上，只能被读取。
    - 成本优势：由于 calldata 是只读并且无需内存分配来保存其数据，因此直接从 calldata 读取通常比先复制到 memory 再读取更便宜（在 gas 方面）。因此当函数参数不需要被修改时，应声明为 calldata（例如 Solidity 中函数参数类型为 bytes calldata 或数组 calldata），以避免不必要的内存复制。
    - 实践建议：若函数只是读取参数（比如验证签名、检查数组元素但不做修改），优先使用 calldata。若确实需要修改数据或需要一个可变的临时副本，再将 calldata 复制到 memory。
- Storage 的性质与昂贵性：
    - Storage 是合约在链上持久化的空间，分为若干 32 字节的存储槽（slot）。每个 slot 的 key（地址）与 value 均为 256 位。合约的状态（例如某个变量的值、映射内容）被持久化在 storage 中。
    - 成本且后果明显：Storage 写入（SSTORE）是 EVM 中成本最高的操作之一。写入不仅消耗大量即时 gas，而且还改变链上状态，这对区块链的存储负担产生长期影响（历史节点存储、回滚等）。因此无论是出于经济性还是出于安全审计角度，都应尽量减少不必要的 storage 写操作。
    - Storage 的组织与查找：视频提到每个合约地址都有自己的 storage，并且 storage 的底层组织依赖 Patricia Merkle Trie（帕特里夏-默克尔树），这是区块链整体状态的一部分。作者明确表示不会在视频中深入 Patricia Trie 的实现细节，只指出这是底层的 persistent（持久化）状态组织方式。
- 设计建议与权衡：
    - 尽量将无需持久性的变量保存在 memory 或 stack。只有在必须持久化（如代币余额、权限标志、重要计数器）时才使用 storage。
    - 在需要修改输入参数逻辑不复杂时，避免把 calldata 完全复制到 memory。将 calldata 的偏移/长度当作指针来处理（如果语言/工具允许）比整体复制更省 gas。
    - 对于复杂的数据结构（如映射内的嵌套结构或大量数组），审计时要关注 storage 的 slot 计算、哈希映射键（例如 mapping 的 slot 是 keccak256(key . slot)）等细节（视频未深入计算公式，但这是 storage 常见审计点，视频提示会在更深入场合探讨）。
- 小结：calldata 与 storage 在成本与生命周期上截然不同：calldata 是廉价的只读输入、适合直接读取；storage 是昂贵的持久化空间、应谨慎写入。了解并应用这一原则对节省 gas 与避免审计问题至关重要。

## 3.5 Opcode（操作码）与字节码执行流程（含函数分派示例）

- Opcode 的定义与作用：
    - 在 EVM 层面，opcode（操作码）是给虚拟机的指令，每条 opcode 对应一个字节的十六进制值，并执行具体操作（算术、逻辑、内存/存储读写、跳转等）。把这些 opcode 串联起来就是合约的字节码（code），这就是合约在链上被执行的“程序”。
    - 举例：ADD（加法）会把栈顶两个 32 字节值相加并把结果放回栈顶；PUSH1..PUSH32 系列会把后续 1 到 32 字节的数据直接压入栈中；MSTORE/MLOAD 在 memory 上读写；SSTORE/SLOAD 在 storage 上读写；JUMP/JUMPI 实现程序计数器（PC）的变更。
- PUSH 与 POP 的用途：
    - PUSHn（n = 1..32）将紧随其后的 n 字节数据压入栈，若不足 32 字节，按左侧补零至 32 字节。PUSH32 可直接把一个完整 32 字节 word 压入栈（例如一个 uint256 最大值会以 32 个 0xFF 字节表示）。
    - POP（0x50）弹出栈顶元素并丢弃，常用于清理不再需要的栈元素，以确保栈深度管理。
- MSTORE / MLOAD 和 SSTORE / SLOAD：
    - MSTORE：从栈顶取两个值（position 与 value），把 value 存入 memory 的 position（以 32 字节为单位）。MLOAD：给定一个 position，从 memory 读取 32 字节并把其压入栈顶。
    - SSTORE / SLOAD：与 storage 交互，SSTORE 将值写入 storage 的指定 slot（高成本且持久化），SLOAD 从 storage 的 slot 读取值（比 SSTORE 便宜，但仍比 memory 读取昂贵）。
    - MSTORE8 存一个字节到 memory，便于对字节级数据操作。
- 字节码与函数分派（function selector）：
    - 函数选择器是 ABI 中的概念：函数签名（例如 "count()"）的 keccak256 哈希的前 4 字节即为函数选择器（function selector）。在 calldata 的最前 4 字节用于标识调用哪个函数。
    - 在合约字节码中，编译器会生成一段“入口分派逻辑”：读取 calldata 的第一 word（CALLDATALOAD），对其右移 224 位（即 >> 224），从 32 字节中提取最右侧的 4 字节（32 位，即函数选择器），再与合约内部已知的函数选择器逐一比较，匹配后跳转（JUMP）到对应函数逻辑的字节码段执行。
    - 举例演示（视频中的 walkthrough）：
        - 入口会先设置 free memory pointer（MSTORE at 0x40 = 0x80）以初始化内存。
        - 检查 msg.value（CALLVALUE）是否为 0，如果函数不是 payable 则需 revert（通过 ISZERO、JUMPI 等实现）。
        - 检查 CALLDATASIZE 是否至少为 4（函数选择器长度），否则 revert。
        - 使用 CALLDATALOAD 获取前 32 字节的 calldata，然后使用 SHR（右移，shift right）224（即 0xe0）位得到 4 字节函数选择器。
        - 编译器会按函数选择器的数值升序进行比较。当函数数量少于（或等于）4 时，会采用线性搜索（逐个比较），当函数较多时会用二分法（binary search）加快分派效率。这一排序与分派策略会影响字节码中比较与跳转的执行路径，从而影响 gas（例如数值较小的函数选择器在比较链上更早命中，可节省比较成本）。
        - 一旦匹配，会 PUSH 对应的跳转目的地址并执行 JUMP 到该位置，之后按该函数的具体字节码实现逻辑（如 SLOAD、RETURN 等）。
- 字节码可视化与调试工具：
    - 视频提到了 evm.codes（一个网站）以及在本地借助工具（如 chisel、Foundry 的 cast 等）查看字节码、分步执行与查看栈/内存/storage 变化的能力。通过这些工具可以逐步追踪 opcode 执行流程，了解在某次交易中内存/栈/存储如何被改写。
- 小结：掌握常用 opcode 和入口分派（function selector 的提取与比较）是读懂合约字节码的核心。字节码层面能够解释为什么某些调用路径更便宜或更昂贵、以及如何在没有源码时定位功能入口，对于高级审计和底层优化非常关键。视频的示例演示了从 calldata 提取函数选择器、按值比较并跳转到函数实现的完整流程。

# 4. 框架 & 心智模型（Framework & Mindset）

- 把 EVM 理解为“有限资源下的四层工作区 + 指令集”的心智模型：
    - 四层工作区（临时/持久/只读/代码）：
        - 短期执行层（Stack）：高速、极短期、受限深度，用于算术与临时传参。把它想象为 CPU 的寄存器堆，是最接近执行单元的数据区。
        - 临时内存层（Memory）：交易期间存在、按需扩展、按偏移读写，适合中等大小的临时数据与构造返回值。相当于进程的堆栈区（但不是 LIFO），需要管理 free memory pointer 来避免覆盖。
        - 输入只读层（Calldata）：外部输入的只读字节序列，廉价读取但不可写。把它当作“外部参数快照”，尽量避免复制到内存。
        - 持久存储层（Storage）：链上持久化、昂贵写入，类似文件系统或数据库，只有在状态必须保存时才使用。
    - 指令集（Opcodes）是操作这些工作区的汇编语言。通过 opcode 的组合来实现合约逻辑，编译器会生成入口分派逻辑、内存初始化、参数解码与函数实现的字节码段。
- 分层设计的实践步骤（如何在合约设计与审计中应用该心智模型）：
    1. 识别数据生命周期：在设计函数时先问“这个数据需要持久化吗？需要临时可变吗？仅需读入一次即可？”如果仅读入一次且不修改，声明为 calldata，避免内存复制；如果需要修改但只在调用范围内临时存在，存到 memory；若要跨交易持久化，写到 storage。
    2. 估算成本影响：把可能发生的 SSTORE、memory 扩展、calldata 复制等操作映射到成本等级（SSTORE 高、memory 扩展中等、calldata 读取低）。在实现前制定性能预算：哪些操作必须优化以降低 gas？是否可以把频繁写入改为批量或延迟写入？
    3. 在字节码层做检查：对审计者或高级开发者，学会在没有源码或想验证编译器生成的行为时，查看字节码并识别入口分派逻辑（CALLDATALOAD + SHR 0xe0 提取选择器、PUSH/JUMP 跳转）和 free memory pointer 初始化（MSTORE at 0x40 = 0x80）。这能帮助快速定位调用入口、判断是否对 calldata 做了不必要的复制、或是否存在异常的内存写入偏移。
    4. 关注边界和异常路径：入口分派会先检查 CALLDATASIZE 与 CALLVALUE（msg.value）是否合法，若不满足则会 revert。审计时不要只看主流程，还要逐条确认这些 guard（校验）逻辑是否覆盖所有边界情况（如超短 calldata、意外收取 ether 等）。
    5. 将 gas 优化与安全并行考虑：有时为了节省 gas 会选择微妙的实现（例如重用 storage slot 或在字节码层做紧凑分派），但这些优化可能降低可读性或引入复杂性，从而增加安全风险。心智模型建议权衡：先保证正确性与安全，然后在确定无风险的前提下逐步优化。
- 审计者应采纳的分析流程（步骤化）：
    1. 源码审阅：从高层看函数接口、参数类型与预期数据流（calldata / memory / storage）。
    2. 编译结果与字节码对照：若可获取编译字节码，检查入口分派、free memory pointer 初始化、以及是否有异常的大偏移 MSTORE（可能指内存稀疏写入）。
    3. 跟踪关键数据（敏感份）：对关键值（授权、余额、限制）追踪其读写路径，验证是否被写入到 storage、是否存在前置检查、是否有竞态或回滚问题。
    4. 运行时模拟：利用工具（evm.codes、Foundry 等）单步执行字节码，观察栈/内存/storage 在关键操作前后的变化，以便发现隐藏逻辑或未覆盖的异常分支。
    5. 优化建议与修复：在确认问题或潜在问题后，提出修复方案（更严格的边界检查、减少 storage 写入、使用 calldata 代替 memory 等），并评估修复对 gas 的影响。
- 心态（mindset）：
    - 从执行层面思考问题：不是只看高级语言语义，而要经常把问题回到“EVM 会怎样执行这段代码”这一层。许多漏洞源于对底层执行顺序、栈/内存/存储行为或 opcode 细节的误解。
    - 循序渐进验证：先通过字节码级别确认入口与 guard，再到内存与 storage 的值流，最后再回到源码层提出更易读、更安全的改写建议。
    - 保守原则：当不确定某个内存/存储交互是否安全时，采用更保守的实现（增加检查、减少不必要的写入），并在注释中记录设计选择的原因。
- 小结：将 EVM 看作“有限资源的多层数据区 + 指令集”的模型，配合分层、步骤化的审计与设计流程，可以在保证安全的前提下做出高效的合约实现与可靠的审计结论。这一心智模型既能指导日常编码，也能指导深入的字节码分析和漏洞调查。

# 总结

视频系统性地讲解了 EVM 中六个数据存储位置的职责与差异，重点深入了 stack、memory、calldata、storage 的布局与成本，解释了 free memory pointer（在 0x40 存放并初始指向 0x80）的作用，展示了如何在字节码层从 calldata 提取函数选择器并进行分派（包括按函数选择器数值排序与线性/二分搜索策略），并强调在合约设计时优先利用 calldata 的只读特性以节省 gas、谨慎进行 storage 写入并避免内存稀疏扩展。整个视频旨在将 EVM 从“神秘的黑盒”转变为可理解、可检验的执行模型，从而帮助开发者与审计者在更底层做出更安全高效的决策。
