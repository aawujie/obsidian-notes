CC 之父又出来爆猛料了！  

在昨天的一期播客访谈中，Claude Code 创建者、工程负责人 Boris 一股脑把 ClaudeCode 早期版本及核心架构、发布前 Anthropic 内部做了哪些讨论和突破、Cowork 的真正的护城河设计、Agent Swarm 的魔力机制等等，全都公之于众了！

可以说，绝对是历史上信息密度最高的一期！

首先，关于 Claude Code 的早期，Boris 坦承其实最初就是个 ChatBot，后面接入了第一个工具：bash 之后才一点点演进成今天的 Agent 形态。

而 Claude Code 本身 整体结构其实也并不复杂，主要有三个部分：一个核心的 agent 循环，一个端到端执行部分，以及围绕安全构建的一整圈系统。其中，安全相关的组件是最为繁杂的。

Claude Code 作为产品发布后，使用率经历了几乎垂直一样的陡升，创始人 Dario 看到数据后甚至惊讶地问 Boris：是不是你强制大家使用了！

对于 10 天就打造出来的 Co-work，外界不少人将他视为一款套壳 Claude 模型的产品，Boris 表示 它本质上就是 Claude Desktop 应用的一部分。但它真正复杂的地方，在于它的安全性。面向不同行业的人士，它必须有更为复杂的护栏和权限设计。

近期大火的 Agent Teams 方面， Boris 特别点出了 Anthropic 内部的一个核心概念： “非相关上下文窗口”。这正是 Agent Teams 最有价值的机制。

他们团队从去年9月就一直在实验，他们发现， 当上下文窗口彼此独立时，你往问题里投入更多 token，反而会得到更好的结果。从某种意义上说，这其实是一种 test-time compute 的方式。

直到 Opus4.6 模型，模型才真正学会这种机制。

此外，他还分享了自己的日常工作流。每天一早起床就会打开 iOS Claude ，启动几个 Agent。工作时，一般 会开 **五个 terminal 标签页** 。 每个标签页里都有一份代码仓库的 checkout。然后他会轮流在每个标签页里启动 Claude Code。几乎每一次我都会先进入 **plan mode** （ 在终端里按两次 Shift+Tab）。如果 terminal 标签页不够用了，我还会把任务“溢出”到 Web 或桌面端去运行。

另外，Boris 还提到了 Anthropic 的团队文化。他透露，内部其实不大写 PRD 文档，也没有强制的工单系统。团队成员更喜欢频繁构建原型。这也是让主持人大为吃惊的地方。

Boris 解释道，因为 Anthropic 还是一家创业公司，很多事情其实不需要靠文档来跟大家对齐。

Anthropic内部的工作特点是这样的：

设计师、数据科学家、甚至财务人员都在写代码。他们会在发布一个功能之前做几十甚至上百个原型。Boris 每天提交 20 到 30 个 pull request，而且几乎不需要手动修改一行代码。同时他们仍然有多层验证体系，比如 **Claude Code** 自己审查代码、自动化 lint 规则、多轮自动测试，以及最终的人类代码审查。

播客最后，Boris 再次提到，他认为我们正经历一个堪比“中世纪印刷机时代”的技术转折。

在这样的时代里，传统的代码执念需要放下，因为模型可以使用任何语言和框架，所以这些问题其实越来越无关紧要。

但做事的方法论、假设驱动的工作方法依旧重要。另外，Boris 提到，保持好奇心、愿意走出“泳道”的能力会越来越重要。

2026，将是一个跨界的通用人才或混合人才之年！工程、产品、商业逻辑同时具备，或者设计、金融或其他领域联系起来的跨学科人才，将会越来越被奖励！

同时，Boris还提到，2026将是一个“ADHD之年”，因为他注意到，系统也正在奖励“上下文快速切换”的能力。

话不多说，聊还很多，下面是小编为大家整理的全球最接近顶尖 Agent 产品的大佬剧透，enjoy！

### 加入Anthropic后，第一个PR就被拒了

**主持人：**  
你加入 Anthropic 之后，我听过一个故事，可以请你确认一下或者补充细节：你提交的第一个 pull request 被 Adam Wolf 拒绝了？

**Boris：**  
对，他当时是我的入职导师。我加入 Anthropic 的时候，其实还在思考自己接下来要做什么。我和很多实验室的人聊过，最后选择 Anthropic 很简单——因为它的使命。 这是我个人最关心的问题：未来会发生什么、我们该如何面对这些变化。看到 AI 带来的巨大变革，我觉得需要一种框架来理解它，也需要认真思考我们在其中扮演的角色。

我其实是个非常狂热的科幻读者，家里有一整面书架都是科幻小说。我很清楚事情可能会走向多糟糕的方向，而在 Anthropic，我看到的是一群 **非常认真思考这些问题的人** 。大家都在问：我们怎样才能让事情朝更好的方向发展？

刚加入的时候，我做了一些入职项目，基本上就是到处试验、写一些小东西。我写的第一个 pull request 是 **完全手写代码** 完成的，因为我以为写代码就应该这样。

**主持人：**  
曾经确实是这样写代码的。

**Boris：**  
没错，以前都是这样。但当时在 Anthropic 已经有一个内部工具叫 **Clyde** ，它是 Claude Code 的前身。那个工具非常原始，用 Python 写的，启动要 40 秒左右，本质上是研究代码，也没有 agent 能力。如果你提示得非常小心、工具用得恰到好处，它其实可以帮你写代码。

于是 Adam 直接拒绝了我的 PR，说：“其实你应该用 Clyde 来做这个。”  
我说，好吧。结果我花了半天时间才学会怎么用这个工具，因为需要传很多命令行参数、各种奇怪的 flag。但一旦用对了，它直接给我生成了一个 **可以工作的 pull request** ，一次成功。

那是 **2024 年 8 月或 9 月左右** 。对我来说，这是我在 Anthropic 的第一个“AI 震撼时刻”。因为我完全没想到模型能做到这种程度。我以前习惯的是 IDE 里的那种 **行级补全** 、 **tab completion** 。我完全不知道模型居然可以直接给我生成一个完整的 PR。

### Boris：Claude Code 最初其实就是个ChatBot

**主持人：**  
当你加入 Anthropic 之后，我们之前做过一次深入讨论，但可以再简单回顾一下：Claude Code 是怎么从一个看起来像“副项目”的东西发展出来的？

**Boris：**  
我一开始做了很多不同方向的尝试。一部分是在产品方向，一部分是 reinforcement learning。我当时特意去研究强化学习，是为了理解我所在那一层之下的技术。我经常给工程师一个建议： **一定要理解你所在层之下的那一层** 。这会给你更多杠杆，让你在自己的层级工作时拥有更深的理解。

十年前这个建议是：如果你写 JavaScript，就去理解 JavaScript VM、框架等等。现在情况有点变化了，现在的建议是： **理解模型本身** 。

后来我做了很多实验，有些上线了，有些没有。某一天我只是想了解一下 Anthropic 的公开 API，因为之前从没用过。我也不想做 UI，只是想快速写点东西。当时还没有 Claude Code，我们还在手写代码。

于是我写了一个小工具，本质上只是一个 **命令行里的聊天程序** ：它调用 Anthropic API，让你在终端里和模型聊天。这在当时其实很正常，因为那时候大家对 AI 的理解基本就是聊天机器人。

工程师往往是最早的采用者。 当 AI 从“对话式 AI”开始转向“Agent AI”时，工程师其实很快就理解了。但如果你今天去问非工程师“AI 是什么”，他们大概率还是会说：就是一个聊天机器人。

所以我对我们后来推出的新 产品 **Co-work** 其实 非常兴奋，因为它会把工程师早期看到的那种能力带给更多人。

回到当时的那个工具：Claude Code 最初其实就是一个聊天机器人，因为那时候我对 AI 的理解也只是这样。后来我们才慢慢意识到，下一个形态会是什么。

### 从聊天机器人到 Agent：模型天生就喜欢使用工具

**Boris：**  
当时我做的那个聊天机器人其实有点用，但本质还是个 chatbot。接下来我做的下一步实验是： **让模型使用工具** 。那时候 tool use 功能刚发布，我完全不知道它到底能干什么，于是就随便试试。我给它接入了一个工具—— **bash** 。

我其实也不知道 bash 能用来做什么，于是就问模型一个问题：“我现在在听什么音乐？” 说实话，我当时都不确定它能不能做到。

结果模型直接写了一个小的 **AppleScript 程序** ，用 `sed` 之类的命令去打开我的音乐播放器，然后查询当前播放的歌曲。这个任务是用 **Sonnet 3.5** 一次完成的。

这是我第二个“AI 震撼时刻”。 我突然意识到一件事： **模型天生就想使用工具** 。只要给它一个工具，它就会想办法用这个工具完成任务。

当时很多人对 AI 编程的理解其实是这样的：把模型放进一个盒子里，然后设计一个接口，让程序调用这个模型。就像写软件时给某个模块写一个 stub，然后说：“这里是 AI”。程序其他部分仍然是普通程序。

但后来我意识到，这种思路其实是错的。正确的思路是： **模型本身就是一个独立系统** 。你给它工具，让它运行程序，让它写程序，但不要把它当成传统系统里的一个小组件。

这其实和 AI 研究里著名的 **“苦涩的教训”（Bitter Lesson）** 很像：很多时候最好的方法是让系统自己去发挥能力，而不是人为限制它。

### Claude Code 发布前的两个突破

**主持人：**  
最早的突破之一，就是给模型 bash 访问权限，然后再逐渐加入更多工具，对吧？

**Boris：**  
对。最早是 bash，然后是文件编辑工具。顺便说一句，最初的三个月其实只有我一个人在做这个项目，后来团队才慢慢扩展。

**主持人：**  
还有一个很有意思的故事。你之前提到，当这个工具开始真正写代码之后，你们在 Anthropic 内部讨论过：要不要只在公司内部使用，因为它让工程团队效率提升非常明显。

**Boris：**  
确实有过这个讨论。最后我们决定发布它，因为这样可以在真实环境中研究 **安全问题** 。在 Anthropic，安全是核心。这个实验室成立的原因就是安全。如果你问任何一个员工为什么加入，大概率都会说这个原因。

- 研究模型安全有很多层次：  
	最底层是 **对齐（alignment）** 和 **机制可解释性（mechanistic interpretability）** ，这是模型层面的研究；
- 再往上是 **评测（evals）** ，相当于把模型放在“培养皿”里进行实验；
- 还有一种方式就是 **真实世界观察** ——把模型放到现实环境中，看用户如何使用它、讨论它，以及出现哪些风险。

通过这种方式，我们学到了很多东西，也让模型变得更安全。现在回头看，当初发布它的决定是完全正确的。

**主持人：**  
从外部看，其实很多工程师看到的是另一幅画面：Anthropic 发布了 Claude Code，一个很强的编程工具。后来能力越来越强，很多人开始把它当成主力开发工具。它现在可能已经是增长最快的开发者工具之一。

CC使用率直线上升，惊到了Dario：

你是不是强制大家用了？

**Boris：**  
Anthropic 本质上是一个研究实验室，也是一个安全实验室。产品更像是附带的东西。我们做产品，是为了服务研究、也为了让模型更安全。

我记得当时有一次内部的发布评审会议，我们在讨论要不要发布这个工具。会议室里有 **Mike Krieger** 、 **Dario Amodei** 等人。我们看了一张内部使用率的图表——那条曲线几乎是 **垂直上升** 。

现在更夸张了。今天在 Anthropic，几乎 **100% 的技术员工每天都在用 Claude Code** 。非技术员工的使用率也在快速上升，比如销售团队已经有接近一半的人在用。

Dario 当时问我一个问题：“为什么增长这么快？你是不是强制大家用？” 我说没有，我们只是提供了一个工具，大家用脚投票。

### AI 写代码的转折点

**主持人：**  
你之前提到过一个时间点——大概在 11 月左右，Claude Code 开始写你所有代码。那个转折点是怎么发生的？

**Boris：**  
那个转折点几乎是瞬间发生的： **Opus 4.5** 出现之后。当时模型还没发布，我们内部在 dogfooding（内部测试）。它的能力明显高了一个层级。

我突然发现自己 **几乎不需要再打开 IDE** 。后来我甚至把 IDE 卸载了。不是刻意的，只是一个月之后才意识到：我已经完全不用它了。

**主持人：**  
很多人都有类似体验。尤其是 Opus 4.5 公布之后，我自己也有同样的感觉：如果在我熟悉的代码库里，它写出来的代码基本和我自己写的一样好；如果是我不熟悉的技术栈，它甚至写得更好。

**Boris：**  
说实话，它确实写得比我好。但我还是想保留一点工程师的自尊。

后来 12 月我去欧洲旅行了一段时间，可以说是“编程度假”。我每天都在写代码，这是我最喜欢做的事情。那段时间我每天可能提交 **10 到 20 个 PR** 。这些 PR **100% 都是 Opus 4.5 和 Claude Code 写的** ，我一行都没改。

一个月之后我统计了一下，模型只引入了 **两处 bug** 。如果这些代码是我自己写的，大概会有二十个 bug。

ClaudeCode之父的开发工作流

**主持人：**  
接下来我们聊聊你的开发工作流。 能不能讲讲你现在是怎么用 Claude Code 的？比如并行工作、一些你和团队总结出来的小技巧？

**Boris：**  
先说一个前提：Claude Code 没有唯一的“正确用法”。我可以分享一些个人经验，但如果有人照搬我的流程，那其实是理解错了。我们在设计 Claude Code 的时候刻意让它保持“可改造（hackable）”，因为每个工程师的工作方式都不同，没有两个人的 workflow 是完全一样的。就像工作站的设置一样：键盘、显示器、桌面布局，每个人都不同。工程师更像是手艺人，会非常在意自己的工具组合，所以不存在统一的标准答案。

就我个人而言，我一般会开 **五个 terminal 标签页** 。每个标签页里都有一份代码仓库的 checkout，相当于五个并行的工作副本。然后我会轮流在每个标签页里启动 Claude Code。几乎每一次我都会先进入 **plan mode** （在终端里按两次 Shift+Tab）。如果 terminal 标签页不够用了，我还会把任务“溢出”到 Web 或桌面端去运行。

以前我经常用 Web 版本，比如 claude.ai/code 这个页面。现在更多使用 **桌面版应用** ，因为更方便。Claude Code 在桌面端其实已经集成了很久，就是 Claude 应用里的一个 code 标签页。我很喜欢它的一点是 **内置了 Git worktree 支持** ，这一点对并行开发特别有用。这样你只需要一个代码仓库，然后系统会自动为不同任务创建 Git worktree，相当于给每个任务一个隔离的环境。

我之所以喜欢这种方式，是因为我其实不太喜欢在命令行里手动折腾 Git worktree。那套命令比较繁琐。简单说，Git worktree 的效果有点像这样：Git 在很低成本的情况下帮你创建多个“代码副本”，每个副本都可以独立工作，也很容易丢弃。所以多个 Claude agent 可以同时跑，而且互不干扰。

最近桌面版已经提供了原生支持，但我其实很长时间还是沿用以前那种多个 checkout 文件夹的方式。慢慢地我开始越来越多使用桌面版，因为这样就不需要维护那么多本地副本了。直接开很多 Claude agent 并行运行就行。

另一个让我很意外的工具其实是 **iOS App** 。现在我每天早上醒来，第一件事就是在手机上启动几个 agent。

**主持人：**  
就是原生的那个 iOS 应用？

**Boris：**  
对，就是 Claude 的原生 App。里面有一个 code 标签页，跑的其实就是同一套 Claude Code。

**主持人：**  
不过它是在云端运行，对吧？

**Boris：**  
对，在云端运行。所以需要简单配置一下环境。好在我们的开发环境很简单，我们主要通过 **hooks** 来做初始化，比如在 session start hook 里自动配置环境。

这其实也是我们把 Claude Code 做得很“可改造”的好处之一。你可以很容易加各种自动化配置。

说实话，这件事我自己也完全没预料到。因为在我的认知里，写代码就是在电脑上。如果六个月前有人告诉我：将来我会有 **三分之一甚至一半的代码是在手机上写出来的** ，我肯定觉得这是疯话。但现在这就是我的日常。

---

**主持人：**  
你现在会同时跑很多并行 agent。你是什么时候开始这么做的？对你的工作方式产生了什么影响？  
我自己其实很少用很多并行 agent，通常最多两三个。我比较喜欢一直跟着 Claude 的过程看它在做什么，比如 Learn Mode 就很好，它会解释每一步。待在一个标签页里跟着模型一起推进，其实也挺快的。所以我很好奇，你是什么时候开始转向并行模式的？会不会感觉失去一些控制？

**Boris：**  
我觉得可以把开发流程分成两种模式。

第一种是 **刚进入一个新代码库的时候** 。这个阶段我非常推荐使用 Learn Mode，特别适合新加入团队的人。我们在 Anthropic 也是这样建议新人。Claude Code 里有个命令 `/config` ，可以选择输出风格，比如 Learn 或 Explanatory。我们一般建议新同事选 **Explanatory** ，因为它对陌生代码库的解释会更详细。

但当你已经熟悉代码库之后，目标就会完全改变。这个阶段最重要的是 **效率和产出** 。你希望尽可能多地把东西做出来、上线、交付。

在 **Opus 4.5** 出现之后，这个能力已经很强了。到了 **4.6** ，基本上只要计划做得好，它几乎每次都能 **一次性完成实现（one-shot implementation）** 。

所以关键其实是： 花一点时间来回调整 **plan** ，把计划做对。

我的流程通常是这样的：  
我在第一个标签页启动 Claude，进入 plan mode，给它一个任务。它开始处理的时候，我马上切到第二个标签页，启动第二个 Claude agent，也进入 plan mode。然后是第三个、第四个。等我再回到第一个标签页时，它通常已经完成计划并给出实现。

ClaudeCode团队如何代码评审：

CC自我验证、修复，人类最后把关

**主持人：**  
当代码产量这么高的时候，一个问题就会出现： **代码评审怎么办？**  
传统的软件开发流程通常是：提交 PR，然后必须有人工 reviewer。比如在 Google，甚至需要两个 reviewer，一个负责功能，一个负责代码质量。 你们现在是怎么处理 code review 的？这个流程发生了什么变化？

**Boris：**  
我先讲讲以前我是怎么做 code review 的。因为以前我不仅写代码很多，其实我也是 **代码评审数量最多的人之一** 。我基本上会审所有人的 PR。

其实，这也是身处不同时区的一个好处。我并不是什么超人，只是因为没有会议而已。我做代码评审的方式是这样的： 每当我需要对某个问题发表评论时，我就把它记录到一个电子表格里，并写清楚问题是什么。 比如说，如果有人在函数里把某个参数命名得很糟糕，我就会把这个问题写进表格；如果有人用了一个不太好的 React 模式，我也会记进去。随着时间推移，我会统计这个表格里的条目。 一旦某一类问题出现了三四次以上，我就会为它写一条 lint 规则，把这个问题自动化处理。 所以过去我的做法就是这样：尽量把问题自动化解决 。我一直在尝试把自己“自动化掉”，因为要做的事情实在太多了。

对工程师来说，这其实是一种超能力——我们可以把那些重复、枯燥的工作自动化。很少有其他职业能做到这一点，而这是工程师独有的能力。我一直很享受这个过程，因为它能给我腾出更多时间，让我专注在自己真正喜欢做的事情上。

现在的做法稍微有点不同，但思路其实很接近。 当 Claude Code 写代码时，它通常会在本地运行测试。有时候它会根据需要自动这样做，甚至还会自己写新的测试用例，相当于先做一轮验证。 当我们对 Claude Code 本身做改动时， 它也会测试自己：它会把自己启动成一个子进程，进行自检，并跑一整套端到端测试。这主要是针对内部的 Claude Code 实现。 换句话说，你会有一整套测试体系来让它自我验证。是的，它真的会在一个 bash 进程里启动自己，然后检查“我现在还能正常工作吗”。

这件事其实挺有意思的，因为我们并没有专门写代码让它这么做。尤其是用 Opus 4 或 4.5 时，它会自发地开始做这种检查，好像本能地想确认系统是否正常。所以流程大概是这样：除了这些测试，我们还会在 CI 里运行 Claude 的 agent SDK，也就是 claudep。换句话说，在 Anthropic，每一个 pull request 都会由 Claude Code 先做一轮代码评审。这个过程大概能捕获 80% 左右的 bug，相当于第一轮评审。 Claude 有时会自动修复其中的一部分问题 ，有些它不确定该怎么处理，就会留给人类工程师。最终一定会有工程师做第二轮代码评审，而且任何代码变更都必须由人类批准之后才能进入系统。

在团队里也是这样：在任何东西进入生产环境之前，一定会有工程师亲自看一遍代码。至于代码评审要不要在所有项目中都这样做，其实取决于项目的用途。如果只是一个个人的小项目，你完全可以直接把代码推到主分支，甚至在 AI 出现之前很多人也是这么干的——不评审，直接上线，或者 SSH 到生产环境里改代码。Claude Code 的最早版本在内部也是这样，我当时就是直接往主分支提交。但只要开始有真实用户，情况就完全不同了。

对于 Anthropic 来说，我们的主要客户是企业，所以安全、隐私和可靠性都非常关键。企业客户对这些要求非常高。因此作为一个企业级产品，系统必须达到一定的安全标准。我们确实用了很多自动化手段， 但至少在目前，人仍然需要参与其中，作为最后的把关者。

引入确定性机制：类型检查器、lint规则

**Boris：**  

有一个大家都知道的问题：LLM 本身是非确定性的。即使 Claude 可以做代码评审并给出不错的反馈，你也无法保证它每次都能发现问题。即使它有能力识别某个 bug，也不能保证每次都会识别出来。所 以问题就变成：在这个流程里有没有引入一些确定性的机制？比如 lint 本身就是非常确定性的工具。

答案是：当然有。我们会使用类型检查器、lint 工具，也会跑完整的 build。Claude 在写 lint 规则方面其实非常强。以前我会用电子表格统计问题，现在的做法是：如果同事提交了一个 pull request，而我觉得这个问题其实可以用 lint 自动检测，我就直接让 Claude 在这个 PR 里写一条 lint 规则。只要运行类似 `/setup-github` 这样的命令，Claude Code 就会安装 GitHub App，然后你就可以在任何 pull request 或 issue 里直接 @Claude。我每天都会用这个功能，非常方便。

所以整体流程会包含一些确定性的步骤 。但与此同时，也有办法让 Claude 的行为变得更接近确定性。例如可以用 best-of-N 的方式，让它多跑几次评审。实现起来其实非常简单：我们内部的 code review skill 是开源的，就在 Claude Code 的仓库里。基本思路就是启动多个并行 agent 进行评审，然后再启动一组去重 agent 来检查哪些结果可能是误报。本质上所谓的 best-of-N，只需要一句话：“Claude，启动三个 agent 来做这件事。”系统就会并行运行这些评审。

CC的架构：核心是一个循环

**Boris：**  

至于 Claude Code 的架构，其实非常简单。最核心的部分就是一个 query loop，再加上一些工具。我们经常删除旧工具、加入新工具，一直在做实验。整体结构可以理解为三个主要部分： 一个核心的 agent 循环，一个端到端执行部分，以及围绕安全构建的一整圈系统。 安全相关的组件其实非常多 ，它们的目的只有一个：确保 Claude Code 在执行任何操作时都是安全的，并且在关键步骤中始终有人类参与。

这里的安全其实包含多个层面。既包括当 Claude 在用户电脑上执行操作时的安全，也包括 Anthropic 在监控潜在风险使用场景时的安全。安全从来没有单一的完美方案，更现实的方式是一层一层叠加防护。我们常用一个“瑞士奶酪模型”来形容：每一层防护都可能有漏洞，但只要层数足够多，整体的风险就会显著降低。最终你只需要计算失败概率里的“九”的数量，然后决定系统需要达到什么样的安全阈值。

以 prompt injection 为例，我们通常会在三个不同层级进行防护。举个场景：Claude 通过 web fetch 获取一个 URL，然后读取网页内容，再根据这些内容在 Claude Code 中执行操作。风险在于网页里可能包含恶意提示，例如让系统删除所有文件夹之类的指令。针对这种情况，我们就会在多个层级进行检测和防护，以确保这种指令不会被执行。

每天它都会观察番茄的生长，而且还显得非常开心。

还有人用 Claude Code 从一块损坏的硬盘里恢复照片，那是他的婚礼照片。

在 Anthropic 内部，我们整个财务团队都在用 Claude Code，销售团队也在用。 换句话说，有很多非工程师用户正在使用它。

当时 Claude Code 已经存在很多不同的使用形态。最早我们是从终端（terminal）开始，然后扩展到了 IDE，比如 VS Code 系列和 JetBrains 系列。

后来我们又做了 iOS 和 Android 应用，还有桌面端、Web 端，以及 Slack 和 GitHub 的应用。这些扩展主要是为了让工程师使用 Claude Code 更方便。

但问题在于，这些形态其实都不是为非工程师设计的。所以 Claude Code 虽然不断演进，但我们始终觉得这里存在一个空缺——还有一个产品可以把这件事变得更简单。

过去几个月里，团队一直在尝试各种方向，思考什么才是正确的产品形态。

后来有人提出一个想法： 如果我们直接把 Claude Code 拿过来，加上一些护栏（guardrails）会怎样？

例如，Co-work 会运行在一个虚拟机里。这只是我们保证安全的方式之一，尤其是为了那些不想去阅读 Bash 命令、也不想搞清楚系统到底在做什么的非技术用户。

于是团队就开始动手做了。整个开发周期大概就是 **10 天左右** ，从头到尾几乎都是用 Claude Code 自己构建的。然后我们就发布了。

**Boris：**  
有些地方的复杂度比你想象得低，有些地方则比你想象得高。

从产品角度来说，其实相对简单，因为它本质上就是 Claude Desktop 应用的一部分。当你下载 Claude 桌面应用时，它其实是一个单独的应用程序，里面有三个标签页：Co-work、Code、Chat。

真正复杂的部分，其实在 **安全性** 。 因为我们知道用户是非技术人员，所以必须确保他们的体验是安全的。举个例子：如果有人打开应用，然后不小心删除了一堆家庭照片，那就非常糟糕。所以我们必须设计系统，避免这种事情发生。

在前端，我们还提供了一整套虚拟机环境，并且有很多操作系统级别的集成，确保用户不会误删文件。

Agent Teams真正的魔力机制

非相关上下文窗口

**主持人：**  
你们最近刚发布了一个新功能——Agent Teams。我理解它的思路是，从原来的单个 agent，变成一个“团队”：一个主 agent 可以把任务分派给不同的子 agent。你们是怎么开始实验这个方向的，又是什么时候决定把它正式发布出来的？

**Boris：**  
我们一直在做各种实验，试图让 Claude Code 的能力发挥得更充分。方法其实有很多种，比如扩展上下文、自动压缩上下文——这样基本就能获得接近“无限上下文”的效果。另一种方法就是使用子 agent，让多个 agent 协作工作 。核心思路其实是：如何从上下文窗口里榨出更多价值。有一个我们内部的概念叫“非相关上下文窗口”。 意思是你可以同时运行多个上下文窗口，但它们彼此是独立的、从零开始的，它们互相并不知道对方的存在。

举个例子，如果模型在同一个上下文窗口里连续做两个任务，第二个任务会知道第一个任务发生了什么，因为它们共享上下文。 但如果是子 agent 的方式，主 agent 只会给子 agent 一个提示，而子 agent 的上下文是全新的 ， 它并不知道父上下文里发生了什么。这就形成了“非相关”的上下文关系。某些场景下你需要共享上下文，而另一些场景下恰恰需要这种独立性。

很有意思的一点是，当上下文窗口彼此独立时 ，你往问题里投入更多 token，反而会得到更好的结果 。从某种意义上说，这其实是一种 test-time compute 的方式。像 Teams 这种功能，我们已经实验了很久，大概从去年 9 月或 10 月就开始了。直到 **Claude Opus 4.6** 出来之后， 模型终于真正学会了如何利用这种结构。 有时候你会看到 agent 之间互相对话、讨论问题，看起来甚至有点像人类交流，很有意思。

当然更重要的是结果确实更好。我们在内部做过很多评估，比如让 Claude 构建一些非常复杂的系统——复杂程度已经超过单个 Claude 能处理的范围。使用 Teams 后，表现明显提升，所以我们觉得现在是发布它的合适时机。不过我们也比较谨慎，目前它仍然是研究预览，而且需要手动开启。原因很简单：这种方式会消耗大量 token，因为本质上是很多个 Claude 同时在运行。

并不是每个任务都需要这样复杂的结构。对于特别复杂的问题，它很有价值，但日常简单任务就没必要。主 Claude 会决定子 Claude 的规则，不过并没有一套固定的配置方法，这完全取决于具体场景。我个人觉得这个机制真正的魔力来自“非相关上下文窗口”的理念， 而不是 agent 的具体配置方式。所以这是一件值得大家多去尝试的事情，没有统一答案。

**主持人：**  
虽然它目前还是研究阶段，但你们有没有看到一些看起来很有潜力的应用场景？这种 swarm 方式是不是已经开始展现出价值？

**Boris：**  
其实有不少功能就是用这种 swarm 方式构建的，比如插件系统。还有很多其他功能也是这样做出来的。所以我觉得，只要你看到单个 Claude 开始吃力的任务，swarm 方式通常就能帮上忙，这是一个很值得研究的方向。

Boris：保持初学者心态！

**主持人：**  
说到变化，我想起你和 **Andrej Karpathy** 去年 12 月的一次交流。当时他说自己从未像现在这样觉得“落后”，因为 AI 的进展太快了。你当时分享过一个例子：你在用传统方式调试一个内存泄漏问题，而 Claude 一次就解决了。这似乎反映出很多人的感受——技术变化的速度太快了。 你自己是怎么适应这种变化的？

**Boris：**  
这件事其实让我挺挣扎的。模型进步的速度太快了，以前对旧模型有效的方法，在新模型上可能完全不适用；而以前无效的思路，在新模型上反而可能突然变得有效。这样的技术其实很少见，所以我也没有太多经验可以借鉴，去判断应该如何应对。对我来说，这是一个必须学习的新能力。

从某种意义上讲，你必须一直保持一种“初学者心态”。我经常提到“谦逊”这个词， 因为你必须在智识上保持谦逊。很多过去被认为是坏主意的想法，现在变成了好主意；反过来也一样。我需要不断提醒自己这一点。 以前在软件行业，如果有人重新尝试一个过去失败过的想法，通常会被问：为什么又要试一次？这其实带有一点 gatekeeping 的意味，但在很多时候也算合理。比如系统架构里，有人提议用微服务，如果三年前已经试过并且失败了，那反对也算有道理，因为技术环境变化不大。

但现在情况不同了。模型每几个月就会进化一次，因此重新尝试旧想法完全有可能成功。我甚至在团队里看到这种现象：一些刚加入团队的工程师，或者工程经验更少的人，有时会做出比我更好的方案。我必须观察、学习，然后调整自己的预期。举个例子，我们发布新功能时，我有时会截一些自己使用产品的截图发到社交媒体，比如 **X (Twitter)** 或 **Threads** ，介绍一下功能。但最近我们团队的 DevRel 同事 Tar 做了一件很有意思的事——他直接把这件事自动化了，让 Quad Code 自己生成产品发布的视频。这种事情以前我只觉得“理论上可能做到”。但他直接就把它实现了。

**主持人：**  
有一件让我觉得有点奇怪、但很多开发者可能也能共鸣的事情。大概从 **Claude Opus 4.5** 开始，我慢慢接受了一个现实——模型写代码已经非常强了。像 **GPT‑5.2** 也给我类似的感觉。现在这些模型写代码真的很厉害。我逐渐意识到，如果我只是想把事情做成，我大概不会再亲手写代码了。如果只是为了享受写代码的乐趣，我当然仍然可以写。但有一点让我感慨很多：为了成为一个好的程序员，我曾经付出过巨大的努力。我还记得自己从最早的“瞎折腾”，到进入大学学习 C 和 C++，那段过程真的非常艰难。

后来在最初几份工作里，我慢慢变得更擅长调试，也逐渐把很多自我认同建立在“我很会写代码”这件事上。过去我们获得工作机会，或者拿到更高薪水，很大程度上就是因为写代码的能力。

后来我在 **Uber** 做工程经理时，我们设计面试流程，会讨论应该考察什么能力。我们会问：开发者大部分时间在做什么？答案是，大约一半时间在写代码。所以面试中大约一半的信号都来自编码能力。很多东西都围绕写代码建立起来，因为它确实很难。

大家都知道，要把代码写好需要毅力，也需要一定的智力。现在出现了一种很复杂的情绪： 一方面看到模型能做到这些事情当然很好，另一方面又感觉好像有某种东西被很快地拿走了。 我自己没想到这种变化会来得这么快。

我们处在一个AI版的印刷机时代

原来被少数人垄断的能力向社会开放了

主持人：

我想很多人都有类似感受。有些人适应得更快，但确实存在一种“失落感”。你是怎么看这件事的？毕竟你在 **Facebook** 写过大量代码，工作之外也写了很多。对很多人来说，你的能力是很难达到的。但现在模型似乎也能做到同样甚至更好的水平。

**Boris：**  
确实有一种变化正在发生：过去只有软件工程师能做的事情，现在越来越多的人都能做了。当我刚开始写代码时，它完全是一件很实用的事情，是一种把事情做出来的手段。后来某个阶段，我开始真正爱上写代码这件事本身——包括编程语言、工具，还有那些背后的设计理念。再后来，我甚至有点“陷进去”了。我还写过一本关于编程语言的书，是关于 **TypeScript** 的。那是我在 **O'Reilly Media** 出版的第一本 TypeScript 书。

后来我还发起过世界上最大的 TypeScript meetup，当时在 **San Francisco** 。那段时间我认识了很多技术偶像，比如提出“响应式通用理论”的 **Chris Cowell** ，还有创建 **Node.js** 的 **Ryan Dahl** 。那是我第一次真正深入进入这个技术社区，也深入理解编程语言和工具本身。

像 TypeScript 这样的语言，其实有一种独特的美感，特别是在类型系统上。 **Anders Hejlsberg** 的设计真的非常出色，比如条件类型（conditional types）这样的概念，还有几乎任何东西都可以成为字面量类型。

对我来说，另一个让我沉迷的领域是 **Scala** ，还有整个函数式编程世界。 直到现在，当我写代码，或者当模型写代码时，我脑子里首先想到的仍然是类型 。 类型签名往往比代码本身更重要。如果类型设计正确，很多事情自然就会变得清晰。 所以在某种意义上，编程确实有艺术的一面。但最终它依然是一种工具，是一种用来构建东西的手段。 它是一种达到目的的方法，本身并不是终点。

我经常用一个比喻来理解我们现在所处的时刻： **Printing Press** （印刷机）。大概在 15 世纪时，情况其实有点类似。当时有一群抄写员，他们掌握写字的技能。虽然我们没有生活在那个时代，但可以想象，那也是一门需要学习、需要设备、需要长期训练的“技艺”。你可能还需要某种赞助或资助才能从事这项工作，因为你需要不断重复抄写同样的内容。能够做到的人并不多，也许地位很高，或者收入不错——我们可以这样假设。

但后来印刷机出现了。在欧洲，当时如果你想成为抄写员，可能需要被某个领主或国王雇佣，还要经过多年的训练。那是一小群特殊的人，他们掌握了书写能力。很多时候连国王或王后自己都不识字。那时识字率非常低，在欧洲可能不到 1% 的人会读写。

印刷机出现之后，事情发生了巨大变化。印刷材料的成本在接下来的几十年里下降了大约 100 倍，而印刷品的数量在接下来的一两百年里增长了大约一万倍。这是第一层变化。识字率的提高则慢一些。后来全球识字率逐渐达到 70% 左右，但这个过程花了两三百年，因为学习读写本身非常困难，需要教育体系，需要纸张和墨水，需要人们有时间学习，而不是整天在农田劳作。工业化的早期阶段才真正让这些条件逐渐成熟。

但关键变化在于： 原本被少数人垄断的能力，突然向所有人开放了。今天我们生活中的很多东西，如果没有这种变化其实都不会存在。 假设制造这支麦克风的人不识字，那么建立现代经济体系都会变得非常困难。很多技术都不会出现。更有意思的是，如果当时的人试图预测印刷机出现之后世界会怎样发展，大概没有人会想到“麦克风”这种东西会诞生。所以我觉得，这是理解今天 AI 时代最好的类比之一。

接下来会发生什么：原型构建者、跨界者

**主持人：**  
你刚才提到有些国王其实并不识字，但他们雇佣抄写员。这个类比其实挺有意思。如果我们坦诚一点看现实，其实很多企业老板也是类似的情况：他们知道自己想做什么产品，但不会写代码，所以必须雇软件工程师来实现。我觉得程序员有时候会调侃那些 CEO，他们跑到团队面前，可能拿着一张手绘原型或者白板草图，说“这个应该很容易做吧”。但他们其实并不了解实现的复杂度。

这里确实存在一种类似的结构：一个人有想法，但需要雇专业人士把它实现出来。想法和实现之间始终存在一道鸿沟。如果类比到印刷机时代，当国王终于可以自己读写信件，就不再需要中间人了，很多事情会变得更高效。当然，从抄写员的角度来看，这并不一定是好消息。不过聪明的抄写员依然可以找到新的角色——毕竟总有人需要写书、运营印刷机等等。

**Boris：**  
对，正是这样。如果你再想想当年的抄写员后来发生了什么，其实他们并没有彻底消失，只是“抄写员”这个身份逐渐消失了。取而代之的是另一类人——作家和作者。之所以会出现这群人，是因为文学市场突然被极大地扩大了。以前抄写员写的东西可能只有少数几个人会读，而印刷机出现之后，作者的数量大幅增加。有些人的作品确实没人读，但也有一些作者获得了远超他们想象的传播范围。这种变化带来了全新的职业形态。

主持人：

我很喜欢这个类比。那么接下来会出现什么？当“任何人都能做到这件事”之后，会诞生哪些今天完全无法预测的新事物？

Boris：

虽然无法准确预测未来，但我们可以看看当下已经在发生什么。如果你观察自己身边的环境，比如在 **Anthropic** 的团队中，那些真正脱颖而出的工程师、构建者，或者技术成员，他们正在做什么？他们具备哪些技能？他们的工作方式又发生了什么变化？其实很难只点出某几个具体的人，因为老实说，这是我职业生涯中见过最强的一群人。

这些人有很多不同的“原型”。有些人是极其出色的原型构建者， 他们擅长把一个想法从零快速推进到“0.5”的阶段，探索有哪些有趣的想法、技术该怎么走。 还有一些人非常擅长找到产品与市场的契合点，也就是把项目从 0.5 推到 1，甚至从 0 到 1。还有一些人跨越多个学科。我越来越多地看到这种人：他们既懂产品工程，也懂基础设施工程，或者同时理解产品和设计，甚至设计与工程之间也能打通。我看到越来越多这种跨界的“混合型人才”。

必须确保安全超正确的方向发展

**主持人：**  
过去一年里，有没有什么信念发生了变化？有没有什么你原本坚信的事情，现在已经被修正甚至彻底放弃？

**Boris：**  
有一件事是关于安全问题。老实说，我以前并不确定安全到底是不是一个非常大的问题。我加入 **Anthropic** 的原因之一，是因为我读了很多科幻小说，我知道如果事情走向糟糕的方向会有多严重。但当时我并没有完全确定风险到底有多大。

不过从公司内部的视角看到过去一年里不断出现的新风险之后，我变得比以前担心得多。这件事对我来说变得非常重要。现在对我而言最重要的问题是：我们如何确保这件事朝正确的方向发展。

2026，会是通才之年

放下代码的执念，保持好奇心

**主持人：**  
可以这么说，在 AI 出现之前你已经是一位非常优秀的软件工程师，而且是非常高产的那种工程师。你当然也是团队的一部分，但从个人能力来说也很突出。那么在今天，有哪些过去的软件工程技能依然很重要，甚至比以前更重要？又有哪些技能可能已经没有那么重要了，甚至可以被放下？

**Boris：**  
我觉得可以被放下的一类东西，是 那些关于代码风格、编程语言、框架之类的强烈执念 。比如 endless 的语言之争、框架之争，我真的很期待这些争论早点结束。因为模型可以使用任何语言和框架，如果你不喜欢，它可以马上帮你重写。所以这些问题其实越来越无关紧要。

但有些能力仍然非常重要。 比如做事要有方法论、要以假设驱动。 无论是产品设计还是工程工作，这一点都很关键。现在整个行业都在经历剧烈变化，我们都在思考下一步该构建什么产品。在这种情况下，以假设为驱动的思考方式就很重要。

在工程日常工作中也是一样，比如调试问题。调试必须非常有条理。模型可以帮助很多，但现在仍然处在过渡阶段，你仍然需要这种能力。至于六个月之后还是否需要，我也说不准。

另外一些越来越重要的能力，是保持好奇心，并愿意走出自己的“泳道”。 如果你是工程师，但同时理解商业逻辑，你就能构建出非常棒的产品。我甚至觉得下一个十亿美元级产品、甚至下一家万亿美元级公司，可能就是由一个人创造的。那个人脑子里有一个好想法，而且能同时从工程、产品和商业的角度思考，或者把设计、金融以及其他领域联系起来。未来的人会越来越多学科融合，这种能力会越来越被奖励。

从某种意义上来说，我觉得今年可能会成为“通才之年”。

还有一个有点有趣的能力其实也开始被奖励了——注意力跨度很短。

2026：ADHD之年

不同上下文之间快速切换

**主持人：**  
注意力很短也会被奖励？

**Boris：**  
是的。比如现在很多年轻人每天在用 **TikTok** 这样的应用。某种程度上，这对社会其实是有风险的，因为我们仍然需要能够深度思考的人，需要能够长时间沉浸在复杂问题里的人，而不是不断跳到下一个想法。

但在今年的工作方式里，某种程度上真的开始奖励这种“快速切换”的能力。我甚至半开玩笑地说，今年可能会成为“ADHD 之年”。

对我来说， 工作越来越像是在不同项目之间跳跃，管理多个并行的任务。重点已经不再是长时间深度工作，而是你能不能在不同上下文之间快速切换 。

**主持人：**  
听起来我可以补充一个词：适应力。你既能深度专注，又能快速切换，而且很愿意根据新的阶段调整自己的工作方式。模型一更新，工作方式就可能再次改变。

**Boris：**  
没错。唯一可以确定的事情是：下一代模型发布的时候，一切又会改变。你必须保持好奇心，也要随时准备调整自己的工作方式。

喜欢读刘慈欣的科幻作品

**主持人：**  
最后一个问题，你有没有推荐的书？

**Boris：**  
我最近有点掉进科幻小说的“兔子洞”。很多人知道写《三体》的刘慈欣 **，但其实他还有很多很棒的作品，尤其是短篇小说。我非常喜欢他的几本短篇集。**

如果有人刚接触科幻，并想读一点更“硬核”的作品，我很推荐 **Accelerando** ，作者是 **Charles Stross** 。这本书几乎像是未来五十年的产品路线图。故事从技术起飞开始，一路讲到 AI 奇点，最后甚至发展到一种围绕木星运行的“群体龙虾意识”。听起来很疯狂，但非常精彩。

这本书真正捕捉到的，是技术加速带来的那种节奏感——越来越快、越来越快、越来越快。这种感觉和今天的现实非常像。

技术类书籍方面，我强烈推荐 **Functional Programming in Scala** 。即使今天语言选择不再那么重要，函数式编程仍然是一种非常优雅的编程艺术。它会彻底改变你思考代码的方式，尤其是如何通过类型来思考问题。如果你读这本书，一定要把练习也做一遍。我自己大概做过三遍。这本书会把“函数式类型思维”深深植入你的脑子里，之后你很难停止用这种方式思考代码。

**主持人：**  
Boris，非常感谢你，这是一场非常精彩的对话。

**Boris：**  
谢谢你，这次交流非常有意思。
