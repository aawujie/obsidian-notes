# Prometheus TSDB 压缩机制与数据丢失防护

## 1. 数据从内存到磁盘

Prometheus 抓到的数据先存在内存（Head block）+ WAL 日志。每隔 **2 小时**，把内存中攒够的数据刷成一个磁盘块（L1 块）。

```
内存 + WAL  ──每2小时──▶  L1 磁盘块（2小时一个）
```

## 2. 什么时候触发压缩

每次刷完盘后，Prometheus **立刻**检查：有没有 3 个相邻的同级别块可以合并？有就合并。

```
3 个 L1（各 2h）  → 合并成 1 个 L2（6h）
3 个 L2（各 6h）  → 合并成 1 个 L3（18h）
3 个 L3（各 18h） → 合并成 1 个 L4（54h）
```

会**链式触发**：合出 L2 后如果凑够 3 个 L2，立刻继续合成 L3，整个过程可以在 0.3 秒内完成。

### 触发时机

| 触发条件 | 说明 |
|---|---|
| 每 2 小时 | Head block 刷盘后立刻检查 |
| 启动时 | Prometheus 启动后立刻检查所有块 |
| 导入后 | 启动加载新导入的块后立刻检查 |

## 3. 压缩具体做什么

三步，**非原子**：

```
① 创建：把 3 个旧块的数据合并写成 1 个新块
② 删除：逐个删除 3 个旧块（先 rename 为 .tmp-for-deletion，再 unlink）
③ 加载：重新加载块列表（reloadBlocks）
```

正常情况下很快（几十毫秒），用户无感知。

## 4. 为什么压缩会丢数据

步骤②是逐个执行的，不是事务。如果中途失败：

```
① 创建新块  ✓
② 删旧块 A  ✓  ← 已删，不可恢复
② 删旧块 B  ✓  ← 已删，不可恢复
② 删旧块 C  ✗  ← 失败！
③ reloadBlocks 失败 → 新块被丢弃
```

结果：A、B 已删回不来，新块也没了 → **数据凭空消失**。

## 5. 真实事故：2026-03-11 权限导致数据丢失

### 背景

用 `sudo docker run promtool` 导入回填数据后，部分块文件属主变成了 `root:root`，而 Prometheus 容器以 `nobody:nogroup` 运行。

### 事故过程

1. Prometheus 压缩时尝试合并 5 个块（覆盖 08:00~14:00）
2. 成功创建合并块（44ms）
3. 逐个删旧块：3 个 `nobody:nogroup` 的块删除成功
4. 删到 `root:root` 的块 → **permission denied**
5. `reloadBlocks` 失败 → 合并块被丢弃
6. 结果：3.5 小时数据凭空消失

### 为什么是隐形炸弹

权限不一致：
- **导入时**不报错（promtool 只写文件）
- **启动时**不报错（Prometheus 只需读权限就能加载）
- **压缩时才爆发**（需要删除权限），此时数据已处于半删除状态

### 修复方式

1. 恢复 `.tmp-for-deletion` 标记的残留块
2. 用 `backfill.py` 重新生成缺失时段的数据
3. 导入后 `chown -R nobody:nogroup` 修复所有块权限

## 6. 防护要点

1. **导入后必须修复权限**：`sudo chown -R nobody:nogroup` 整个数据目录
2. **启动前必须校验权限**：确认所有块属主为 `nobody:nogroup`
3. **操作前必须备份近期块**：复制最近 48 小时的块到备份目录
4. **磁盘空间要充足**：压缩时旧块和新块短暂共存，空间不够也会失败

## 7. 关键参数

| 参数 | 默认值 | 说明 |
|---|---|---|
| `--storage.tsdb.min-block-duration` | 2h | L1 块的最小时间跨度 |
| `--storage.tsdb.max-block-duration` | 按保留期自动计算 | 压缩后块的最大时间跨度 |
| `--storage.tsdb.retention.time` | 15d | 数据保留时间，超过的块整块删除 |

## 一句话总结

> 每 2 小时刷盘，刷完立刻 3 合 1，合并时先写新再逐个删旧，删到一半失败就丢数据。权限不一致是隐形炸弹，导入时不报错启动时不报错，压缩时才爆。
