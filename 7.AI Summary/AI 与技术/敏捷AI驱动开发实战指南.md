# 敏捷 AI 驱动开发（Agile AI‑Driven Development）实战方法 —— 用 AI 代理可复用、可扩展地构建产品

## 概述

- 问题：随性“vibe coding”虽然有趣，但难以产出可维护、可扩展的产品。AI 辅助随写容易产生结构混乱、不断修补破坏、成本失控的问题。
- 目标：把传统敏捷流程与 AI 代理（agent）结合，形成一套可复现、可交付、可扩展的工作流，用以构建从简单到复杂的应用（单页网站、SaaS、移动端、多服务系统等）。
- 核心收益：节省时间与金钱、降低试错成本、便于扩展与维护、支持持续交付。

## 方法概述

把产品构建拆成明确的阶段与角色，用 AI 代理完成各阶段产出，然后按“故事（story）”逐条实现。关键要点：

- 先做足前期规划（业务需求、技术架构、任务分解），避免边写边猜。
- 所有文档尽量结构化（Markdown），放入项目知识库（例如 AAI 文件夹），便于在 IDE 中被开发代理读取。
- 每个实现单元是“可独立执行”的 story，包含上下文、数据模型、文件位置、测试与验收标准。
- 建立自动化测试，逐步积累覆盖率（目标 80–90%），确保新增功能不破坏既有功能。

## 角色与职责（AI 代理化的敏捷团队）

### 业务分析师（Business Analyst，BA）

- 任务：与产品持有人/创意方交互，整理产品概念、核心用例、用户目标和边界条件。
- 产出：精炼的需求要点或初稿 PRD（产品说明）。

### 项目经理（Project Manager，PM）

- 任务：基于 BA 输入做深入调研（技术选型、竞品、最佳实践），生成可实现的产品路线图与 MVP 定义。
- 产出：详细 PRD 或研究报告，明确实现范围与里程碑。

### 架构师（Architect）

- 任务：将 PRD 转化为技术架构决策，明确语言、框架、库、数据库方案、部署与安全策略、数据模型等。
- 产出：架构文档（包括数据模型、接口、模块划分、部署管道、第三方服务列表等）。

### 产品负责人（Product Owner，PO）

- 任务：把架构与 PM 输出拆解成按优先级的、可执行的任务列表（granular task list）。
- 要求：任务必须足够细致与有序，使经验较少的开发代理也能逐条实现，包含所有手动设置步骤（账号、环境变量、权限等）。

### Scrum Master / 敏捷组织者

- 任务：把任务组织成 Epics 与 Stories；确认每个 story 的上下文、依赖顺序、验收标准与估时；分配执行顺序。
- 产出：按迭代的 backlog（故事清单），每个故事带有执行上下文。

### 开发代理（Developer Agent）

- 任务：每次从 backlog 中取出一个 story（新聊天线程），实现代码、编写/运行测试、提交变更并触发 CI/CD。
- 流程：实现 → 单元/集成测试 → 修复直到通过 → 推送并合并。

## 文档与交付物（必备）

- PRD（产品需求文档）：目标用户、关键用例、MVP 特性列表、成功指标。
- 架构文档：技术选择、模块划分、数据模型、数据库 schema、API 设计、部署与安全。
- 任务列表（PO 输出）：细粒度任务、顺序、所需权限/账号、手动步骤说明。
- Epics 与 Stories：每故事包含上下文、输入数据、期望输出、文件路径、依赖项、验收标准与测试用例。
- 项目知识库：所有文档统一转成 Markdown，存放于项目仓库/AAI 文件夹，供开发代理读取。

## 故事设计要点（模板建议）

每个 story 至少包含：

- 标题与唯一 ID
- 目标描述（一句话）
- 上下文：本 story 所在的 epic、已完成的前置故事
- 详细需求：功能点、界面或 API 行为
- 数据模型：需要的 schema、字段定义
- 文件/路径约定：应放置/修改的文件位置
- 技术依赖：所需包、环境变量、外部服务
- 验收标准（Acceptance Criteria）：可执行的断言或测试用例
- 测试指引：如何运行测试，期望通过的断言
- 备注：手动操作步骤（若有）、安全注意事项

## 实现流程（执行顺序）

1. BA 与 PM 明确产品与 MVP。
2. 架构师输出详尽架构文档。
3. PO 拆解并生成有序的任务清单。
4. Scrum Master 编排 Epics/Stories，生成 backlog。
5. 将所有文档转为 Markdown 并存入项目知识库（AAI 文件夹）。
6. 在 IDE（如 Cursor）中，按顺序让开发代理逐个打开 story（新 chat），实现并运行测试。
7. 每个 story 通过后合并到主分支，触发 CI/CD 部署（如适用）。
8. 持续累计测试覆盖率，确保回归稳定。

## 测试与质量保障

- 强制为每个 story 编写对应的自动化测试（单元测试、集成测试、端到端测试视情况而定）。
- 目标测试覆盖率：80–90%（越高越能保证持续交付的稳定性）。
- 在 CI 中运行全部测试，失败则阻止合并。
- 定期进行安全审计（依赖检查、秘钥泄露检查、权限配置检查）。

## 成本控制与实操建议

- 在前期规划与文档工作可使用 Gemini / OpenAI 等的高级思考模式（低成本产出结构化文档），大幅降低在 IDE 中的试错消耗（例如 cursor 的 token/credit）。
- 把“账户设置”“环境配置”“密钥存储”等操作列成 enabler stories，决定哪些由代理自动完成、哪些由人工处理，从而节省云服务或 AI 消耗。
- 尽量把大型查找、研究任务留给 PM/BA 阶段完成，而不是在编码阶段频繁向模型查询。
- 将长期重复使用的 prompts、story 模板、代码片段纳入知识库，复用可降低后续成本。
- 在使用付费 AI 资源时，优先用较低成本模型完成初稿，再用高阶模型做精炼与复杂推理。

## 常见工具与技术栈建议（可替换）

- 文档与编辑：Markdown、Git、README、Wiki
- IDE / agent 平台：Cursor（示例）、本地 IDE + agent 集成
- LLM 平台：OpenAI、Google Gemini（用于高级思考、文档生成）
- 部署/后端示例：Vercel（部署静态/前端）、Supabase（后端 DB/认证）、第三方 API
- 前端框架：React / Vue / Svelte（按需要）
- 测试框架：Jest / Mocha / Playwright / Cypress（按场景）

## 实施清单（一步步执行）

9. 定义产品愿景与 MVP（BA + PM）。
10. 生成 PRD 与路线图（PM）。
11. 输出技术架构与数据模型（架构师）。
12. PO 拆解为细粒度任务并排序。
13. Scrum Master 生成 epics/stories，定义验收标准。
14. 将所有文档转换为 Markdown，放入 AAI 文件夹与仓库。
15. 在 IDE 中按顺序让开发代理逐个实现 story；每个 story 都要有测试并通过。
16. 通过 CI/CD 自动化构建、测试、部署。
17. 持续积累测试覆盖、监控与文档维护。

## 注意事项与常见坑

- 不要直接在未规划的单个对话中让模型无限改代码（容易耗费、产出混乱）。
- Story 需足够具体，避免让代理“自行决定太多”，以减少不一致实现。
- 合理划分哪些步骤人工完成（账号、信用卡、敏感配置），哪些交给代理。
- 定期回顾并调整 backlog 与架构，保持文档同步。

## 总结

将敏捷思想与 AI 代理结合，先把“想法—需求—架构—任务”做成结构化产物，再让代理逐条实现，是构建稳定、可维护、可扩展产品的可行路径。该方法能显著降低反复调试和成本浪费，既保留了用 AI 快速试验的乐趣，又能保证工程质量与演进能力。建议按本文流程试点一个小型 MVP，从 BA→PM→架构→PO→Scrum→开发代理逐步落地，逐渐完善模板与知识库。
