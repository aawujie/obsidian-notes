## 📌 什么是时序数据库

**时序数据库 (Time Series Database, TSDB)** 是专门用于存储、查询和分析**带时间戳的数据**的数据库系统。

### 核心特征

```
┌─────────────────────────────────────────────────────────┐
│                    时序数据三要素                        │
├─────────────────────────────────────────────────────────┤
│                                                         │
│   时间戳 (Timestamp)  →  数据什么时候产生的              │
│        ↓                                                │
│   指标名 (Metric)     →  数据是什么                      │
│        ↓                                                │
│   值 (Value)          →  数据的具体数值                  │
│                                                         │
│   可选：标签 (Tags/Labels) →  数据的维度标识             │
└─────────────────────────────────────────────────────────┘
```

### 典型时序数据示例

| 时间戳 | 指标名 | 标签 | 值 |
|--------|--------|------|-----|
| 2026-03-09 12:00:00 | cpu_usage | host=server1, core=0 | 45.2 |
| 2026-03-09 12:00:01 | cpu_usage | host=server1, core=1 | 52.8 |
| 2026-03-09 12:00:02 | memory_used | host=server1 | 8192 |
| 2026-03-09 12:00:03 | http_requests | method=GET, status=200 | 1523 |

## 🆚 时序数据库 vs 传统数据库

### 核心差异对比

| 维度       | 时序数据库 (TSDB)                                            | 传统关系数据库 (RDBMS) |
| -------- | ------------------------------------------------------- | --------------- |
| **数据模型** | 时间 + 指标 + 值                                             | 行 + 列 + 表       |
| **写入模式** | 追加写入 (Append-only)                                      | 随机读写 (CRUD)     |
| **查询模式** | 时间范围查询为主                                                | 复杂 JOIN、条件查询    |
| **索引结构** | <span style="color:rgb(255, 77, 77)">时间索引 + 标签索引</span> | B+ 树、哈希索引       |
| **数据更新** | 极少更新/删除                                                 | 频繁更新/删除         |
| **压缩效率** | 极高 (10:1 甚至更高)                                          | 一般 (2:1 ~ 5:1)  |
| **并发写入** | <span style="color:rgb(255, 77, 77)">极高 (百万点/秒)</span>  | 中等              |
| **事务支持** | 弱或无                                                     | 完整 ACID         |
| **典型场景** | 监控、IoT、金融行情                                             | 业务系统、OLTP       |

### 架构设计差异

```
┌─────────────────────────────────────────────────────────────┐
│                    传统数据库架构                            │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   应用 → SQL 解析 → 查询优化 → 执行引擎 → 存储引擎           │
│                        ↑                                    │
│                   复杂的优化器                               │
│                   支持多表 JOIN                              │
│                   事务锁管理                                 │
│                                                             │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│                    时序数据库架构                            │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   应用 → 写入 API → 内存缓冲 → 持久化 → 压缩存储             │
│              ↓                                              │
│         时间分区 (按时间分片)                                 │
│         自动降采样 (Downsampling)                            │
│         自动过期 (Retention Policy)                          │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 🔧 时序数据库的核心技术

### <span style="color:rgb(255, 77, 77)">1. 数据存储优化</span>

#### <span style="color:rgb(195, 117, 255)">时间分区 (Time Partitioning)</span>

```
数据按时间自动分片：
┌─────────┬─────────┬─────────┬─────────┬─────────┐
│ 2026-W10│ 2026-W11│ 2026-W12│ 2026-W13│ 2026-W14│
│ (旧数据)│         │ (当前)  │         │ (未来)  │
└─────────┴─────────┴─────────┴─────────┴─────────┘
     ↓           ↓           ↓           ↓
  冷存储      温存储      热存储      预分配
```

**优势**：

- 快速定位时间范围
- 便于数据过期删除（直接删分区）
- 支持冷热数据分离

#### <span style="color:rgb(195, 117, 255)">列式存储 (Columnar Storage)</span>

```
传统行式存储：
┌──────────────────────────────────────────┐
│ [t1, cpu, 45.2] [t2, cpu, 46.1] [t3...] │  ← 行
└──────────────────────────────────────────┘

时序列式存储：
┌─────────────┬─────────────┬─────────────┐
│ 时间戳列    │ 指标名列    │ 数值列      │
│ [t1,t2,t3]  │ [cpu,cpu...]│ [45.2,46.1] │
└─────────────┴─────────────┴─────────────┘
     ↓              ↓              ↓
  高效压缩      字典编码      Gorilla 压缩
```

### <span style="color:rgb(255, 77, 77)">2. 数据压缩技术</span>

#### <span style="color:rgb(195, 117, 255)">Gorilla 压缩算法 (Facebook 开源)</span>

```
原始时间戳：1709956800, 1709956801, 1709956802, 1709956803
存储差值：  1709956800, +1, +1, +1  → 大幅压缩

原始数值：  45.2, 45.3, 45.2, 45.4, 45.3
XOR 编码：   45.2, Δ1, Δ2, Δ3, Δ4  → 只存变化位
```

**压缩效果**：

- 时间戳：<span style="color:rgb(195, 117, 255)">差值编码 + 可变长度整数</span>
- 数值：<span style="color:rgb(195, 117, 255)">XOR 编码 + 浮点压缩</span>
- 整体压缩率：<span style="color:rgb(195, 117, 255)"><b>10:1 ~ 50:1</b></span>

#### <span style="color:rgb(195, 117, 255)">Delta-of-Delta 编码</span>

```
时间戳序列：1000, 1001, 1002, 1003, 1005
第一次差值：   -, +1, +1, +1, +2
第二次差值：   -,  -,  0,  0, +1  → 大部分为 0，极易压缩
```

### <span style="color:rgb(255, 77, 77)">3. 降采样 (Downsampling)<br></span>
```
原始数据 (1 秒 1 点)：
┌────────────────────────────────────────────────┐
│ ● ● ● ● ● ● ● ● ● ● ● ● ● ● ● ● ● ● ● ● ● ● ● │  86400 点/天
└────────────────────────────────────────────────┘
              ↓ 降采样 (5 分钟平均)
┌────────────────────────────────────────────────┐
│   ●   ●   ●   ●   ●   ●   ●   ●   ●   ●   ●   │  288 点/天
└────────────────────────────────────────────────┘
```

**降采样策略**：

| 原始粒度 | 降采样后 | 聚合函数 | 保留时长 |
|----------|----------|----------|----------|
| 1 秒 | 1 分钟 | AVG/MAX/MIN | 7 天 |
| 1 分钟 | 5 分钟 | AVG | 30 天 |
| 5 分钟 | 1 小时 | AVG | 90 天 |
| 1 小时 | 1 天 | AVG | 1 年 |

### <span style="color:rgb(255, 77, 77)">4. 连续查询 (Continuous Query)</span>

```sql
-- InfluxDB 示例
CREATE CONTINUOUS QUERY "cpu_5m_avg" ON "monitoring"
BEGIN
  SELECT mean("value") INTO "cpu_5m" 
  FROM "cpu_usage" 
  GROUP BY time(5m), "host"
END

-- 自动每 5 分钟执行一次，预计算聚合结果
```

## 🏆 主流时序数据库对比

### 产品矩阵

| 数据库                 | 语言   | 开源  | 特点                   | 适用场景 |
| ------------------- | ---- | --- | -------------------- | ---- |
| **Prometheus**      | Go   | ✅   | Pull 模型、PromQL、云原生   | 监控告警 |
| **InfluxDB**        | Go   | ✅   | 高性能、SQL 类查询          | 通用时序 |
| **TimescaleDB**     | C    | ✅   | PostgreSQL 扩展、完整 SQL | 混合负载 |
| **OpenTSDB**        | Java | ✅   | HBase 后端、大规模         | 超大规模 |
| **VictoriaMetrics** | Go   | ✅   | Prometheus 兼容、高性能    | 监控存储 |
| **ClickHouse**      | C++  | ✅   | OLAP、列式存储            | 分析查询 |
| **TDengine**        | C    | ✅   | 国产、高性能、IoT           | 物联网  |
| **QuestDB**         | Java | ✅   | 低延迟、SQL 支持           | 金融行情 |

### 详细对比

#### Prometheus
```yaml
优点:
  - 云原生事实标准
  - PromQL 功能强大
  - 生态系统完善 (Exporters + Grafana)
  - 轻量级，部署简单

缺点:
  - 单点存储 (需 Thanos 做高可用)
  - 不适合长期存储
  - 不支持 SQL

典型用户: Kubernetes、微服务监控
```

#### InfluxDB
```yaml
优点:
  - 写入性能极高 (百万点/秒)
  - 查询语言类似 SQL
  - 内置降采样和连续查询
  - 单二进制部署

缺点:
  - 开源版功能受限 (2.0 后)
  - 集群版需商业授权
  - 内存占用较高

典型用户: IoT、应用性能监控
```

#### TimescaleDB
```yaml
优点:
  - 完整 PostgreSQL 兼容
  - 支持 SQL + JOIN
  - 自动分区和压缩
  - 生态丰富 (所有 PG 工具可用)

缺点:
  - 性能略低于专用 TSDB
  - 需要 PostgreSQL 知识

典型用户: 需要 SQL 的时序场景
```

#### VictoriaMetrics
```yaml
优点:
  - Prometheus 远程存储兼容
  - 性能优于 Prometheus 10 倍
  - 单节点支持百亿级数据点
  - 资源占用低

缺点:
  - 生态相对较小
  - PromQL 子集支持

典型用户: 大规模 Prometheus 存储
```

### 性能对比 (参考)

| 指标 | Prometheus | InfluxDB | VictoriaMetrics | TimescaleDB |
|------|------------|----------|-----------------|-------------|
| 写入吞吐 | 50K 点/s | 500K 点/s | 500K 点/s | 100K 点/s |
| 查询延迟 | 中 | 低 | 低 | 中 |
| 压缩率 | 5:1 | 10:1 | 15:1 | 8:1 |
| 内存占用 | 低 | 高 | 中 | 中 |
| 集群支持 | 需 Thanos | 商业版 | 内置 | 内置 |

## 📊 时序数据库的应用场景

### 1. IT 监控与可观测性

```
场景: 服务器、容器、应用性能监控

数据流:
  应用/系统 → Exporter → TSDB → Grafana → 告警

常用指标:
  - CPU、内存、磁盘使用率
  - 网络流量、连接数
  - 请求延迟、QPS、错误率
  - JVM 指标、GC 次数
```

### 2. 物联网 (IoT)

```
场景: 传感器数据采集

数据流:
  传感器 → MQTT/HTTP → TSDB → 分析/告警

常用指标:
  - 温度、湿度、压力
  - 设备状态、位置
  - 能耗、电压、电流
  - 振动、噪声

特殊需求:
  - 海量设备 (百万级)
  - 高频采集 (秒级甚至毫秒级)
  - 边缘计算 + 云端存储
```

### 3. 金融行情

```
场景: 股票、期货、加密货币行情

数据流:
  交易所 → WebSocket → TSDB → 量化分析

常用指标:
  - OHLCV (开高低收量)
  - 订单簿深度
  - 成交明细
  - 资金费率

特殊需求:
  - 低延迟写入和查询
  - 高精度时间戳 (纳秒级)
  - 数据完整性要求高
```

### 4. 业务分析

```
场景: 用户行为、业务指标追踪

数据流:
  应用埋点 → 消息队列 → TSDB → BI 仪表盘

常用指标:
  - DAU/MAU、留存率
  - 转化率、漏斗
  - GMV、订单量
  - 用户活跃度

特殊需求:
  - 多维标签分析
  - 与业务数据关联
  - 支持复杂聚合
```

### 5. 工业监控

```
场景: 生产线、设备监控

数据流:
  PLC/SCADA → 网关 → TSDB → 预测性维护

常用指标:
  - 设备运行状态
  - 产量、良品率
  - 能耗、效率
  - 振动、温度异常

特殊需求:
  - 高可靠性
  - 实时告警
  - 预测性分析
```

## 🚀 选型指南

### 决策树

```
需要完整 SQL 支持吗？
    │
    ├── 是 → TimescaleDB / QuestDB
    │
    └── 否 → 继续
            │
            需要云原生/监控场景吗？
            │
            ├── 是 → Prometheus / VictoriaMetrics
            │
            └── 否 → 继续
                    │
                    需要极致写入性能吗？
                    │
                    ├── 是 → InfluxDB / TDengine
                    │
                    └── 否 → 继续
                            │
                            需要超大规模 (百亿点) 吗？
                            │
                            ├── 是 → OpenTSDB / VictoriaMetrics
                            │
                            └── 否 → 根据生态选择
```

### 选型检查清单

| 问题 | 考虑因素 |
|------|----------|
| 数据量级？ | 百万点/天 vs 十亿点/天 |
| 查询延迟要求？ | 秒级 vs 毫秒级 |
| 需要 SQL 吗？ | 团队技能、现有工具 |
| 需要集群吗？ | 单点 vs 分布式 |
| 保留时长？ | 7 天 vs 1 年+ |
| 预算？ | 开源 vs 商业 |
| 生态需求？ | Grafana、BI 工具集成 |

### 推荐组合

| 场景 | 推荐方案 |

| **Kubernetes 监控** | Prometheus + Grafana + Thanos |

## 💡 最佳实践

### 数据建模

```
✅ 好的设计：
  - 指标名简洁明确 (cpu_usage, http_requests)
  - 标签数量适中 (3-5 个)
  - 标签值基数有限 (避免 user_id、email)
  - 统一命名规范 (snake_case)

❌ 坏的设计：
  - 指标名包含标签信息 (cpu_usage_host1 → 应该用标签)
  - 标签过多 (>10 个)
  - 高基数标签 (user_id、订单号)
  - 命名不统一 (cpuUsage vs cpu_usage)
```

### 写入优化

```yaml
批量写入:
  - 单次写入 1000-5000 点
  - 避免单点高频写入
  - 使用异步写入

压缩传输:
  - 启用 gzip/snappy 压缩
  - 远程存储使用 Write-Ahead Log

时间对齐:
  - 客户端时间同步 (NTP)
  - 避免时间戳乱序
```

### 查询优化

```promql
✅ 高效查询:
  - 使用索引标签过滤
  - 限制时间范围
  - 使用降采样数据
  - 避免全表扫描

❌ 低效查询:
  - 无时间范围限制
  - 正则匹配高基数标签
  - 大范围聚合
  - 复杂子查询
```

### 运维建议

| 事项 | 建议 |
|------|------|
| **存储规划** | SSD + 按时间分区 |
| **内存配置** | 写入缓冲 ≥ 1GB |
| **备份策略** | 每日快照 + WAL 归档 |
| **监控指标** | 写入延迟、查询延迟、磁盘使用 |
| **容量规划** | 预留 50% 余量 |
| **数据保留** | 热数据 7 天 + 冷数据 90 天 |
