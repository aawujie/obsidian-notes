## 一、人才素养：工程师 + 研究员的结合

做大模型需要的人才不是明确分工的两类人，而是**每个人都需要具备两方面的素养**：

- **算法出身的人**：不要"等人喂饭"，有需求要尝试自己解决
  - 小模型随便写，大模型需要知道如何拆到多卡上
  - 心态："我想要这个东西，希望有人给我写好" → 很难做出前沿的东西

- **系统出身的人**：不要自我陶醉
  - 问题：不知道业务要什么，不知道模型想做成什么样子
  - 避免："我做了一个很牛逼的系统，但到底有没有用没人知道"

## 二、两个重要原则

### 1. 工程师需要自己构建工具

- **目的**：有真实需求去解决，不是为了显示自己很厉害
- **例子**：Deepspeed、Megatron 等工具的实现

### 2. 对数字敏感

作为系统工程师，应该知道带宽和延迟的数据：

- 什么东西速度应该是多快
- 模型有多少参数量、Attention 有多少、FFN 有多少
- **能算出来** vs **了然于心** 是两码事

**为什么重要**：
- 对数字不熟悉，有问题你不知道
- 模型训练每一步时间是多少？如果没有概念，不知道跑得快不快
- FFN 层中间宽度变成 4 倍——这是非常好的数字，是局部最优

**常见误区**：
- 看论文只看模型结构
- 不看参数怎么调、数据集怎么清洗
- 结果：讲得头头是道，但模型训不出来

## 三、GPU 计时方法

### 问题：GPU 编程是异构编程

```python
# ❌ 错误的计时方式
start = time.time()
output = model(input)
end = time.time()
# 这只是 CPU 把命令告诉 GPU 的时间，不是实际执行时间
```

### 正确方法

**方法 1：强制同步**
```python
torch.cuda.synchronize()  # 计时前后都加上
```

**方法 2：CUDA Event（异步计时）**
```python
start_event = torch.cuda.Event(enable_timing=True)
end_event = torch.cuda.Event(enable_timing=True)

start_event.record()
output = model(input)
end_event.record()

torch.cuda.synchronize()  # 拿时间时同步
elapsed_time = start_event.elapsed_time(end_event)
```

**优点**：
- 计时更精确
- 开销比 synchronize 小
- 不打扰原有程序的时序

### Warm Up

同一个操作前几次会比较慢（涉及 Benchmark 算法选择、显存管理等）：

```python
# 先空跑若干次，不计时
for _ in range(10):
    model(input)

# 稳定后再计时
```

## 四、性能指标

### 1. GPU Utilization（GPU 利用率）

**含义**：在过去采样周期内，至少有一个 kernel 在任意流处理器核心上运行的时间比例

**结论**：
- Util 低 → 代码性能差（GPU 没干活）
- Util 高 ≠ 代码性能已挖掘到位

**Util 虚高的原因**：
- 通信忙等（多机/多卡训练中常见）
  - 有些卡算完了，在等另一些卡通信
  - 利用率 100%，但实际没干活
- 算子实现太差（GPU 一直在算，但有更好的算法）

**Util 低的解决**：
- 可能卡在 CPU 或内存上
- Data Loader 有问题，数据没读上来
- 解决：优化数据格式、开更多 data worker、CPU 数据预处理

### 2. 更高级的指标

| 指标              | 说明                            |
| --------------- | ----------------------------- |
| SM 占用率          | 比 Util 更好，观察算子实现              |
| Tensor Core 利用率 | 大部分计算是矩阵乘法，最能代表 GPU 是否好好使用    |
| 功率              | A100 额定 400W，至少跑到 350W 以上才算跑满 |

### 3. 核心原则

> **程序的执行时间（挂钟时间）是唯一一致且可靠的指标**

其他指标可能被 hack，真实运行时间最可靠。

## 五、MFU / HFU / MBU 指标

### MFU（Model Flops Utilization）

**定义**：模型实际实现的算力 / 硬件理论提供的算力

**计算方法**：
1. 计算模型理论计算量
   - 前向计算量：矩阵乘法 2×M×N×P
   - 反向计算量 ≈ 2×前向（梯度要传两个方向）
   - 粗略估算：计算量 = 6×参数量×数据量

2. 实测模型运行步数 × 每步计算量 = 实际实现计算量

3. MFU = 实际实现计算量 / 硬件理论算力

**示例**：
- 模型实际算力 100 TFLOPS
- 硬件理论算力 200 TFLOPS
- MFU = 50%，上限是再翻一倍

### 📐 MFU 计算详细示例

> **注**：FLOPS = Floating Operations Per Second，FLOPs = Floating Operations。所以 FLOPs / 时间 = FLOPS

**案例**：

| 步骤 | 说明 | 数值 |
|------|------|------|
| 1 | 模型每次 fwdbwd 计算量（理论值） | 10000 TFLOPs |
| 2 | 训练 5 步用时（实测） | 30s |
| 3 | 硬件配置 | 16 张 A100，每张 312 TFLOPS |
| 4 | 系统实际算力 | 10000 × 5 / 30 = **1666.7 TFLOPS** |
| 5 | 硬件理论算力 | 312 × 16 = **4992 TFLOPS** |
| 6 | **MFU** | 1666.7 / 4992 = **33.39%** |

**参考**：PaLM: Scaling Language Modeling with Pathways 的 Appendix B 有关于 GPT 类模型的 MFU 计算的更详细说明。

### 💡 MFU 的核心价值

> **MFU 是唯一一个跨系统可比的指标**

比如说有两个公司各自训练了自己的大模型：
- 显卡型号不一样
- 显卡数量不一样
- 网卡规格不一样
- 模型尺寸不一样
- 模型结构不一样
- 训练框架不一样

**最后互相比较谁训练系统牛逼，就是比谁的 MFU 高。**

### HFU（Hardware Flops Utilization）

**定义**：GPU 实际执行的计算量 / 硬件理论提供的算力

**与 MFU 的区别**：
- MFU 分子：模型**需要**多少计算量
- HFU 分子：GPU**实际执行**了多少计算量

**重计算（Recomputation）的影响**：
- 前向算完丢掉中间值，backward 时重新算一次
- 模型理论只需算 1 次，实际执行了 2 次
- HFU 会比 MFU 高（硬件塞满了，但训练不一定变快）

**目标值**：
- MFU：希望达到 50% 以上
- HFU：可能到 70%（因为有重计算）

### MBU（Memory Bandwidth Utilization）

**适用场景**：推理系统（受限于显存带宽）

**示例计算**（7B 模型，半精度）：
- 参数量：7B × 2 字节 = 14GB
- 生成每个 token 延迟：14ms
- 实际带宽：14GB / 14ms = 1TB/s
- A100 理论带宽：2TB/s
- MBU = 50%

**目标值**：推理系统希望达到 70%-80%

## 六、复杂度 vs 常数

> **做算法的人讲复杂度，做系统的人讲常数**

### 例子：线性 Attention

- Transformer Attention 复杂度：O(n²)
- 线性 Attention：O(n) 或 O(n log n)

**为什么当时没火**：
- 4K/8K 上下文长度下，t²和 t log t 差别不大
- 实现差一点或常数大一点，反而更慢

**为什么最近火了**：
1. 上下文更长了（1M+），复杂度优势显现
2. KV Cache：线性注意力缓存是常数级别，显存负担小
3. 并行算法改进，更匹配 GPU

### 例子：Cum Sum

```python
# 方法 1：循环（计算量最小，但串行）
for i in range(n):
    result[i] = sum(x[:i+1])

# 方法 2：矩阵乘法（运算量大，但可并行）
# 用下三角矩阵乘向量
# 对于短序列，矩阵乘法可能更快
```

## 七、性能优化方法

### 1. Profile（性能分析）

> **不能被测量的东西，没有办法优化**

**双重含义**：
- 速度：知道每一部分运行时间
- Metric：有合适的指标衡量模型表现

### 2. 阿姆达尔定律

```
加速比 = 1 / [(1-p) + p/s]

p = 可被优化/并行化的部分占比
s = 该部分的加速倍数
```

**启示**：
- 优化前先估计上限
- 如果某部分占比很少，优化意义不大
- 示例：MFU 20% → 优化到头最多加速 5 倍

### 3. 瓶颈分析

**原则**：优化最慢的地方

- 优化非瓶颈地方：效果微乎其微或不在关键路径上
- 示例：Data Loader 慢 → 预处理数据、用 GPU 做预处理、换更高带宽集群

**优化停止点**：
- Data Loader 时间 < 模型训练一步时间
- 再快也不影响总训练时间，可以停了

### 4. 训练时间分解

```
Step Time = Data Time + Forward Time + Backward Time 
          + Worker Gap + Gradient Reduction Time 
          + Optimizer Time + Other Time
```

| 部分 | 说明 |
|------|------|
| Data Time | Data Loader 读取数据时间（可隐藏在计算中） |
| Forward/Backward | 前向/反向传播时间 |
| Worker Gap | 分布式训练中卡之间的速度差异 |
| Gradient Reduction | 梯度同步时间（大模型通信量大） |
| Optimizer Time | 优化器更新时间 |
| Other Time | 监控、日志等杂项 |

**Worker Gap 的原因**：
- 随机波动
- 工作负载不均衡（如 MoE 专家分配不均、不定长输入）
- 解决：监控卡健康状态、数据 shuffle 和 packing

## 八、工作习惯建议

### 1. 第一性原理思考

**信念**：计算机是人造产物，所有问题一定能找到原因

**避免基于类比/试错**：
- ❌ "Torch 新出了 torch.compile，试一下"
  - 加速了 20% → 上限在哪？不知道
  - 没效果 → 是没用还是瓶颈不在这？不知道
- ✅ 先详细分解训练时间，知道瓶颈在哪，再优化

### 2. AI 写代码要克制

> **What AI gives, AI takes away**

AI 帮你写代码省时间，但会生成一堆垃圾（代码/文档）消耗你阅读时间。

**正确用法**：
- AI 是手，你是脑
- 你知道在做什么，AI 帮你执行
- 示例：算 MFU 需要知道 Flops 怎么算
  - ❌ 让 AI 调包算（可能统计不全）
  - ✅ 自己知道怎么算，AI 当计算器用

### 3. 公共基线（标准化）

> **只有一块表的人知道现在几点，有两块表的人永远无法确认时间**

**标准化的三个要点**：

1. **共享**
   - 相同配置、相同代码（同一个 commit）
   - 避免：各 fork 分支，改不同地方，数据无法对齐

2. **可复现**
   - Bitwise 可复现性
   - 相同机器、代码、配置 → 结果一样
   - 大模型需要能回到"现场"分析问题

3. **最小可行基线测试**
   - 分级测试：单机单卡 → 单机多卡 → 多机多卡
   - 避免：直接交 48G 任务跑 18 小时，挂了白跑
   - 实验分级：
     - 改模型架构 → 等比例缩小实验（学习率 schedule 也要缩放）
     - 验证稳定性 → 大模型 + 少步数
     - 数据实验 → 小尺寸模型迭代（7B 以内）

## 九、研究故事

### ResNet 的诞生

- 不是拍脑袋想的"加跨层连接"
- 基于对 GoogLeNet 的分析
- 发现最重要的是 1×1 分支
- 简化成无任何变换的连接 → ResNet

### MMDetection 的级联策略

- 用几分之一算力做实验
- 实现更快迭代
- 在 academic budget 下做出很多成果

### DeepSeek V3 的 FP8 训练

研发过程：
1. 确定 FP8 格式（分析 BF16 模型的权重/激活值分布）
2. 不同层可能需要不同精度
3. 更精细的操作（每几个 token 一起做量化/反量化）
4. 目标：FP8 训练曲线尽量匹配 BF16

### 奇葩 Bug 合集

1. **48 台机器不收敛**
   - 32 台和 64 台都收敛，48 台不收敛
   - 原因：48 不是 2 的幂，浮点数除法误差累积
   - 解决：先加梯度，最后统一除 48

2. **断点恢复参数没恢复**
   - 参数超过 4GB，序列化协议只恢复了前 4GB
   - 后面部分是随机的

3. **H 卡比 A 卡训练结果好**
   - A 卡 40GB，H 卡 80GB
   - A 卡显存小 → 模型切分到更多卡上
   - 初始化 bug：参数切得越碎，不同卡上参数越像，独立性差

## 十、目标与展望

### 短期目标

1. **共享基线**
   - 所有人同一基线
   - 确定式、可复现

2. **一分钟拉起训练**
   - 从提交任务到第一步 forward/backward < 1 分钟
   - 多机环境下是挑战（分布式环境初始化可能就要 1 小时）
   - 重要性：修 bug 改 5 次，1 小时拉起 vs 1 分钟拉起 → 半天 vs 半小时

3. **做好 CI 和 Code Review**
   - 不流于形式

### 中期目标

4. **更好的训练 Profile**
   - 训练时间分解准确

5. **理解训练动态**
   - 模型训练过程中参数/激活值怎么变
   - 示例：AMP 训练到后期 log scale 固定在 256
   - 知道后就不需要每次都做 scaling，手动操作即可

### 如何实现一分钟拉起

- 训练不要做别的工作（数据过滤、清洗、安装包等）
- 大项目 import 很花时间（几秒到几十秒）
- 网络优化（协议配置、环境变量）
- 强制指定拓扑（多机训练）
- 支持假数据/随机数据调试
- 编译结果缓存（Triton、compile 等）
- 多卡模型预 warm up（流水并行）

### 长期目标

6. **更好的离线指标**
   - 不可能每个模型都上车测

7. **数据驱动的实验**
   - 现状：手动挑选数据分布
   - 目标：建立表征模型
     - 对语料打分（质量、多样性）
     - 近似/严格去重
     - 聚类、采样
   - 示例：发现模型在某些场景不好 → 用表征模型检索相似片段 → 收集数据 → 调整类别采样比例

## 十一、关键公式速查

### 计算量估算

```
前向计算量 ≈ 2 × M × N × P（矩阵乘法）
反向计算量 ≈ 2 × 前向
粗略估算：计算量 = 6 × 参数量 × 数据量
```

### MFU 计算

```
MFU = (实测步数 × 每步计算量) / (硬件理论算力 × 时间)
```

### MBU 计算（推理）

```
MBU = (参数量 × 精度字节数) / (生成延迟 × 硬件理论带宽)
```

### 阿姆达尔定律

```
加速比 = 1 / [(1-p) + p/s]
```
