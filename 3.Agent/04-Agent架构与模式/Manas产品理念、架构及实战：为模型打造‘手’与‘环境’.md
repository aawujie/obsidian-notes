# 1 Metadata

- Title: 把“大脑变成手”：Manas 的产品理念、架构与实战（演讲整理）
- Author: Tao（昵称 hik，Manas 联合创始人、首席产品官，口述稿整理）

## 2 Overview

在这段演讲中，Tao（hik）介绍了 Manas 的核心理念：不是再训练“更聪明”的模型，而是为现有强大的基础模型“打造手”（即执行能力、工具与环境），让模型能在现实世界中长期、复杂地执行任务。他阐述了 Manas 的设计出发点、典型应用场景、系统架构（把每个 agent 配一个完整的云端虚拟机、丰富的工具与私有数据接入）、与模型选择逻辑（偏好能做长时程规划与工具调用的模型），以及工程上为提升函数调用/工具使用而采用的“planner 注入”机制。结论是：通过“less structure, more intelligence”（更少预设流程、更多依赖基础模型的智能），Manas 将“手”赋予模型，从而在消费级市场实现长期、复杂任务代办能力。

按主题来梳理

### 3 演讲者自我介绍与产品愿景

- 内容摘要与背景
    - 演讲者自我介绍为 Tao（昵称 hik），现为 Manas 的联合创始人兼首席产品官。Tao 提到自己有 28 年编程经验，但在 AI 领域属于“新人”，仅进入两年。他两年前的目标是打造一款“能为单个用户 24 小时产生影响力”的产品（即持续性、高频率地服务单一用户），当时这是他的梦想；而在 Manas 的实践下，他认为年底可以实现这个目标（演讲中原话）。
    - 名字来源：Manas 不是英语单词；灵感来自 MIT 的座右铭 Mens et Manus（拉丁语，意为“心与手”或“思与行”）。演讲者解释他们取名为 Manas（或 manus 口述中有拼写混用）是因为他们希望把“手”交给很聪明的模型——过去两年出现的基础模型相当像“人类的大脑”，非常聪明，但缺少“手”，无法在现实世界去执行和产生持续影响。
- 为什么需要“手”
    - 演讲者回忆自己童年在中国1996年只有在学校的机房才有两次/周的计算资源，说明只有大脑（想法）而没有机器（手）难以把想法付诸实践。他用这个比喻来说明：现在的基础模型有能力推理、生成内容，但如果我们只“给它一支笔和纸”——也就是只给模型文本输入/输出，而不提供可执行环境和工具，模型难以在现实世界中真正完成复杂、多步骤的任务。
    - 因此 Manas 的使命是“给模型手”：不是继续训练模型（或做 post-training），而是搭建执行环境与一整套工具链，让模型去“做事”。
- 设计上的直接目标（产品层面）
    - 将复杂任务做成可被模型在云端代办的服务，从而实现长期（24 小时）对单个用户的持续价值。
    - 面向消费市场（非仅企业），把复杂外部数据源、第三方 API 与私有数据库的接入在后端预先解决，让普通用户无须写代码或调用 API 就能享受完整的代理能力。

### 4 两个具体用例：搬迁选址与空房布置（内部与用户案例）

- 用例一：全球扩张中的办公室选址（内部使用示例）
    - 背景：Manas 在短时间内开设新办公室（新加坡、东京、旧金山等），需要为 40 人团队在东京挑选合适办公室并解决住宿（accommodation）问题。
    - 用户如何交付任务：团队向 Manas 发出一个 prompt（任务指令），说明需求：为 40 人寻找可容纳 40 人的办公室，并同时给出附近住宿建议。演讲者指出，Manas 收到 prompt 后会自己“有计划地执行”——浏览器自动爬取、检索、比对多个网页并进行研究。
    - Manas 的输出形式（在约 20–24 分钟内完成）：
    - 交互式地图：显示 Manas 所找到的 10 个候选，蓝色标记代表办公地点，绿色标记代表附近住宿选项。用户可以直观看到每个选项在地图上的相对位置。
    - 逐项推荐与理由：第一页举例，Manas 首选是 Shibuya Scramble Square（演讲者原话），并解释这个办公室适合的原因，但同时指出租金太高。Manas 也给出了其它更便宜且离办公地点很近（如约 200 米）的候选，并给出价格与推荐理由。
    - 结果表格：页面底部提供了候选的概览表（包括价格、距离、优缺点等），方便比较与决策。
    - 价值点：在短时间内完成大量人工调研、整合异构信息（地图、租金、距离、住宿选项），并以直观的交互方式给出决策支持，体现了 agent 在“端到端任务执行”上的能力。
- 用例二：把空房图片变成可购买的家具布置（对外用户示例）
    - 任务流程（演讲中按步骤描述）：
    - 用户上传空房间图片给 Manas。
    - Manas 对房间做视觉分析：判断房间风格、布局，以及需要哪些家具（例如沙发、茶几、书柜等）。
    - Manas 前往第三方零售网站（演讲里说是 “EKS” 网站，后续又出现 “EKA” 拼写，原话模糊——此处保持原文并注明不确定性），在该网站上浏览、筛选符合风格与尺寸的家具。
    - Manas 抓取相应家具的图片并生成合成图（将真实网站的家具合成到房间照片里），同时生成一份文档列出每件家具的购买链接与参数。
    - 用户收到最终合成图片与商品清单（带点击即可跳转购买的链接）。演讲者补充：目前还不能自动完成付款，但未来三个月内可能会支持支付（演讲中为推测式表达）。
    - 价值点：把视觉理解、网页检索、选择、图像合成与产出购买路径这整套流程连成端到端体验，用户可获得“一站式家居布置到购买”的体验，而非只收到零碎建议或商品列表。

### 5 灵感来源：从 Cursor 得到的设计启发与“右侧面板”理念

- Cursor 给团队的启示
    - Cursor（一个代码编辑器产品，演讲者提及）对团队启发很大，三位创始人本身都是长期程序员。Cursor 能让人即使不熟悉某个编程语言也能通过自动补全/生成代码解决任务，这本身很强大。
    - 更有趣的现象是：很多“老程序员”用 Cursor 时并不看左侧代码（即他们并不检视或评估生成的代码），他们只是重复按“接受（accept）”让工具为他们完成日常任务（例如数据可视化、批处理、文件格式转换等）。这些用户的目标不是为了有可复用的代码；他们只想得到结果。代码对他们只是中间步骤，而不是最终产物。
- Manas 的反向思考与右侧面板概念
    - Cursor 的界面通常是“左侧写代码、右侧运行结果”。Tao 提出构建“右侧面板”的概念：把“执行”与“自动化”部分放在云端，让用户不必关心代码本身，只需下达任务并获取结果。也就是把“执行的环境和工具”彻底云端化，减少用户对本地环境和代码的依赖。
    - 为什么要放在云端而非本地？演讲中给了几个原因：
    - 安全性：在本地运行自动化工具可能需要安装依赖、修改系统配置，这有潜在安全风险。
    - 不打扰用户：云端运行可以让用户把注意力放回到其他事情上，任务提交后可以关掉设备或放到口袋里，系统完成后再通知用户结果。
    - 可控性与环境一致性：云端虚拟机可以预置必要工具与版本，减少因本地环境差异导致的失败。
- 从“写代码为王”到“结果为王”的产品理念转变
    - 在这个转变中，代码成为工具链的一部分，但不再是用户必须理解或管理的部分。Manas 的目标是把复杂度隐藏在云端，把“任务—执行—结果”做成闭环的用户体验，从而降低用户门槛并提高可用性。

### 6 Manas 的核心组件与技术栈设计（给 agent 一台“电脑”、私有数据库接入、个人逻辑系统）

- 三个关键组件（演讲者强调的核心要素）
- 给每个 Manas agent 一个完整的云端“电脑”
    - 每个 agent 被分配一个功能齐全的虚拟机（VM），包含文件系统、终端（terminal）、VS Code（编辑器）和一个真实的 Chromium 浏览器（不是 headless，无界面交互能力）。
    - 作用与价值：模型可以在这个完整环境中执行真实的操作，比如解压大量 PDF、读取文件、运行脚本、在浏览器里真实点击与导航等。相比仅靠文本 API 或虚拟工具接口，这种“真实环境”极大拓展了 agent 的能力边界。
    - 举例：用户上传一个包含数百个 PDF 的压缩包，agent 可以在 VM 内解压、逐个解析并将非结构化数据抽取成结构化表格，完成端到端的数据整理工作。
- 预付并接入私有数据库 / 第三方数据源（为普通消费者做好数据接入）
    - 考虑到许多重要的信息并非公开网页（或需要付费、需要 API 认证、或保存在私人/企业数据库中），Manas 在后端为用户预先接入并付费这些私有数据源或 API，避免普通用户需要自己写代码调用 API。
    - 目的：降低消费级用户的技术门槛，使其能直接获得实时金融数据、受限数据或需要授权才能访问的内容。
- 个人逻辑系统（personal logic system / personal knowledge）
    - 考虑到在长期、多轮任务中频繁向用户确认重复性细节会降低体验，Manas 实现了一个“可教的个人逻辑系统”：用户可以在某次交互中把偏好或工作流程以“确认”的方式存入系统（例如：“在开始调研前先与我确认所有细节”）。一旦用户把这个规则/偏好录入，Manas 会在未来的相关任务中遵循该规则并先行确认。
    - 对比之处：演讲者提到 OpenAI 的 Deep Research（演讲中称为“deep research”体验）会不断抛出多个问题来明确上下文；而 Manas 的做法是允许用户把确认策略存成个人逻辑，从而在后续自动化中省去重复确认的步骤或在需要时自动执行确认。
- 这些组件如何协同产生价值
    - 单独看每一项都很重要，但真正让 Manas 能做复杂任务的是三者组合：有执行环境（云 VM），有丰富/受限的数据源可用（预接入的私有 API），还有可以被教导的长期偏好/流程（个人逻辑），三者结合使得 agent 能高质量、长时程地自动完成任务，而不是一次性地回答问题。

### 7 核心理念：Less Structure, More Intelligence（更少预设流程，更多依赖基础模型智能）

- 概念阐述（原话的核心观点）
    - Manas 在官网底部写着一句话大意为 “less structure, more intelligence”（更少的结构化流程、更多交给模型的智能）。演讲者强调，他们在产品中并没有给 agent 预定义许多固定的工作流（原话：“zero predefined workflows”），虽然网站上展示了 42 个用例，但这些用例并非通过硬编码流程实现，而是通过非常简单但稳健的结构把尽可能多的决策权和推理能力留给基础模型去处理。
    - 这种做法的核心是：提供足够的上下文、工具与执行环境，但避免把任务拆分成大量手工写死的子 agent（多角色 agent）或一系列强约束的流程。Tao 认为，多角色指定（例如“你是搜索 agent、你是编码 agent”）本身是对模型能力的限制，会限制基础模型的潜力发挥。
- 原因与效果（为什么这样做、更少结构带来的好处）
    - Emergence（能力的涌现）：Manas 在发布时把 42 个用例放到网站上，表面看像是预设流程，但其背后核心是零预定义工作流，复杂能力是从简单结构与强模型能力中“涌现”出来的。演讲者举例说明：一些复杂的 deep research（深度调研）场景，不是通过专门训练模型或硬编码流程实现的，而是从整体框架中自然而然出现的能力。
    - 灵活性与速度：少量结构化约束意味着产品能更快地支持新的用例，团队不需要为每一个新场景构建专门的流水线或训练任务，从而在“创新速度”上占优（后文在 Q&A 中也提到这点：与其靠一项技术长期独占，不如靠快速迭代和利用全球最好的模型）。
    - 依赖更强的基础模型：这种方法的前提是基础模型在长时程规划、工具调用与推理上已经足够强（或至少足够能理解上下文并执行计划）。在演讲中，Tao 指出他们在早期尝试了很多模型，但发现只有某些模型/版本在“长时间规划（long horizon planning）”和持续 agentic loop（执行—观察—再决策）上表现得更稳健，因此他们选择了这类模型作为后端。
- 与“更多结构”的对比（何时需要结构化）
    - Tao 并不是完全反对结构化：在某些场景下（例如对极高可靠性的任务或需要严格审计的企业场景），更多的结构化与硬性工作流仍然有价值。但对于消费级、需要快速响应与适配多变场景的产品，更多地给模型以自由并提供执行能力，能带来更大的产出与更快的产品迭代速度。

### 8 为何选择（演讲中称的）“cloud sol / cloud 4”模型，以及为工具调用做的工程补丁

- 三个选择模型的理由（Tao 的论点）
- 长时程规划能力（long horizon planning）
    - 在标准的对话/问答场景中，模型通常倾向于在一两轮内给出答案，这符合传统 chat 对话的优化目标。但 agentic 场景通常需要 30–50 步操作或更多（演讲中举例），模型需要意识到自己在一个长期循环里，持续收集信息并逐步执行计划。演讲者指出，他们尝试过很多模型，发现许多模型在经过几次迭代后会“认为已经足够”并提前返回答案，只有所谓的“cloud sol”系列模型（演讲原称）表现出能把任务看作一个长回路并持续迭代的能力。
    - 备注：演讲中多次提到“cloud sol 3.7”以及“cloud 4”，这里保留原名（演讲者口述中存在拼写/发音差异，本整理未做额外更正）。
- 工具使用与 function-calling 的支持（工具调用能力）
    - Manas 的 agent 在 VM 中抽象了约 27 个工具（演讲数字），agent 必须在合适的时机、用正确的参数去调用这些工具。早期云端模型在同步工具调用（sync tool）方面的支持不足，Manas 团队为此实现了“coot injection”（演讲中术语）机制：在每次函数调用前，先由一个专门的 planner agent 做推理，生成调用参数与计划（即先做 reasoning），再把这段推理注入到主 agent 中去执行函数调用。这个工程补丁显著提升了工具调用的准确性与稳定性。
    - 随后（演讲中提到最近的模型更新）一些模型原生加入了对同步工具调用的支持（演讲中称在 Cloud 4 有更好的原生支持），验证了他们早期的工程思路。
- 与浏览器/电脑交互对齐（alignment with agentic usage）
    - 因为 Manas 的 agent 要大量与真实浏览器和电脑交互，所选择的模型需要在“与计算机/浏览器交互”这类场景上有良好对齐（即在训练或调优时更多强调这类交互任务），据说 cloud 模型在这方面投入了更多资源，因此是更合适的选择。
- 代价与投入（一个事实）
    - 演讲者坦言：他们在模型（cloud）上烧了很多 token，示例性数字为 “第一 14 天花费了 100 万美元在 cloud 模型上”（演讲原话）。这个数字被用来说明他们为何被邀请上台以及他们在早期验证产品时的高昂成本。

### 9 现场 Q&A 的要点（浏览器理解中视觉 vs DOM、如何保持公司竞争力、本地部署计划）

- 问题一：浏览器交互里，理解网页更多依赖视觉（screenshot）还是解析网页代码（DOM / 文本）？
    - Tao 的回答要点：他们参考并借用了一个开源项目（浏览器代理类项目，演讲中称为 “browser use”），并采用了其与浏览器通信的协议部分（但没有采用其 agent 框架）。当 Manas 在浏览器里抓取上下文时，会把三个部分发送给基础模型：
    - viewport 内的文本（即可直接抓取的文本片段），
    - viewport 的截图（screenshot），
    - 带有 bounding boxes（边界框）的截图（用于告诉模型画面中哪些区域可点击或是重要）。
    - 由此可见，他们并不是单纯靠视觉或仅靠 DOM 解析，而是把“文本 + 视觉（截图） + 可交互的视觉定位（带边界框的截图）”三者组合起来作为上下文供模型决策。这样既保留机器可解析的文本信息，也给模型视觉感知的证据来判断页面布局、按钮位置等。
- 问题二：如何作为一个初创公司在基础模型迅速进步的环境中保持竞争力？
    - Tao 的回答要点：他们并不把赢得竞争寄托于某个固定模型或技术（因为技术会迅速过时）。相反，他们强调两点：
    - 创新的速度（pace of innovation）：快速迭代产品以应对用户需求和市场变化，而不是依赖单一技术壁垒。
    - 架构的灵活性与模型选择的灵活性：他们的 agent 框架设计得足够灵活，可以快速接入并利用世界上最好的模型，因此当更好的基础模型出现时，他们可以迅速切换并获益。
    - 举例说明：Deep research 这种用例在 Manas 中占用户使用的相当比例（演讲中提到约 20% 的用户每天进行深度调研），但 Manas 并没有为这一专门写很多代码；相反，这是从整体框架中自发涌现的能力，这证明了少结构设计在产品创新速度上的优势。
- 问题三：是否有计划把浏览器放在用户本地（以使用本地 cookie / 账户）而非云端？
    - Tao 的回答要点：目前没有把浏览器放到本地的计划。原因包括：
    - 他们希望用户能“把注意力交还给自己”，不必持续关注手机或电脑屏幕；云端处理可以让用户提交任务后离开，任务完成后再收到通知。
    - 安全与一致性考量：云端可以统一环境（例如 Linux VM、计划中的 Windows / Android VM），减少本地环境差异与安全风险。
    - 他们确实计划在云端支持多种虚拟环境（除了 Linux，还计划支持 Windows、Android 等），但总体方向仍以云端为主。

Framework & Mindset（可抽象出的体系与思维模型）

A. “Hands for Models” 思维模型（把执行权交给模型的环境化策略）

- 核心观念
    - 传统观点：训练或微调更强的“脑”来处理问题（更多模型能力）。Manas 的观点是：现有的“脑”已经足够聪明，真正瓶颈在于“手”——也就是模型能否实际在现实世界中执行复杂任务（操作浏览器、处理文件、调用私有 API、发起支付等）。
- 实施步骤（从产品到工程的可操作化路径）
- 为 agent 提供一个功能齐全的运行环境（VM），包括文件系统、终端、编辑器、浏览器。这样模型不仅能“思考”，还能“动手”执行。
- 在该环境中预置用户常用的工具（例如 27 个工具的抽象），并定义统一的工具调用接口，便于模型学习在何时触发何种工具。
- 集成外部数据源与私有 API（演讲中为消费端预先付费接入），使 agent 能访问到许多公开网页之外的重要信息。
- 设计用于长期任务的管理策略（例如任务队列、通知、断点续跑），让用户可以在任务进行时不必持续监控。
- 在用户层面，提供可教的个人逻辑系统（把用户偏好、确认策略写入），减少重复性确认并提升长期使用体验。
- 成效与心态转变
    - 从“把代码交给用户”转向“把任务交给 agent，用户得到结果”。这意味着产品关注点从让用户编写/维护脚本转向如何把正确的环境、工具与上下文交给模型，让模型在云端可靠地“做事”。

B. “Less Structure, More Intelligence” Framework（弱流程、强模型驱动）

- 核心观念
    - 在消费级 agent 产品中，过度预设各类 agent 类型、分角色或写死大量工作流，会限制模型潜在能力并拖慢产品迭代速度。相反，提供一个简单而健壮的基础结构（足够的上下文与工具），并把更多的决策与流程交由强模型来完成，能带来 emergent 能力和更快速的创新。
- 操作化路径（建议步骤）
- 设计简洁的 agent 核心结构：统一的输入/输出规范、标准化工具接口、共享的执行环境与日志体系。避免为每个用例做专门的流程引擎。
- 把“常识性规则”或“高频策略”让用户可通过个人逻辑系统注入，而非硬编码在系统层面。这样系统既保持灵活又能满足个性化需求。
- 在部署阶段，侧重于给模型提供丰富的上下文（截图、文本、工具可用性、历史操作记录），而不是添加更多中间角色或分工。
- 在出现需求降级或高监管需求时，再考虑引入更严格的流程或审计模块（例如企业合规场景）。
- 风险管理与注意事项
    - 依赖基础模型的能力意味着当模型表现不稳时，系统可能出现错误或偏差。要通过监控、回滚策略与“人工审查环”来缓解风险。
    - 为关键任务或高敏感性场景保留额外的结构（例如多级确认、审计日志、可重播的操作记录）以保证安全与合规。

C. 工程实践心智模型：工具调用与 Planner 注入（提高函数调用成功率）

- 问题背景
    - 在 agent 产品里，正确地调用工具（包括函数名称与参数）是高质量执行的关键。基础模型有时无法直接产生准确的调用参数或在多步骤任务中丢失上下文。
- 解决思路（planners + injection 模式）
- 引入专用的 planner agent：在需要执行具体函数/工具前，先由一个专门的推理模块（planner）负责把任务拆解成具体的调用计划，并生成详尽的参数与中间校验点。
- 将 planner 的输出注入主 agent：把 planner 的 reasoning（推理过程与参数建议）作为上下文附着到主 agent 的函数调用请求中，主 agent 再执行实际函数调用。
- 在函数调用后，把执行结果（observation）回传给主 agent 与 planner，形成闭环，便于主 agent 做后续决策或 planner 做下一步的规划修正。
- 随着底层模型（演讲中提到的新模型版本）原生支持同步工具调用（sync tool），可以逐步把 planner 的某些职责内置或简化，但在早期阶段 planner 注入是提高可靠性的有效工程手段。
- 可衡量指标（如何验证效果）
    - 函数调用成功率（正确调用方法与参数）
    - 任务完成时间与所需交互轮数（少轮交互代表计划更好）
    - 失败回滚率与人工干预率（越低越好）

### 总结（短结语）

Tao 的演讲把 Manas 的核心理念、工程实践与实际案例串联起来，强调的中心思想是：不要再只造“更聪明的脑袋”，而要为这些脑袋造“手”与“环境”，让其在云端长期、稳定地执行复杂任务。为此，Manas 采用了每个 agent 独立 VM、预接入私有数据源、可教的个人逻辑系统、以及偏向“less structure, more intelligence”的设计哲学，并在工程上用 planner 注入等手段补强工具调用的可靠性。演讲也覆盖了模型选择（偏好能做长时程规划与工具调用的模型）、浏览器交互的视觉/文本混合上下文策略，以及为何坚持云端执行而非本地化的理由。
