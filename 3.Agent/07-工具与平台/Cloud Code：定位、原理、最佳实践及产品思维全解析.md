# 1. Metadata

- Title: Cloud Code 最佳实践（演讲整理）
- Author: Cal（Anthropic 应用 AI 团队）

# 2. Overview

这段演讲介绍了 Cloud Code（Claude Code）的定位、内部工作原理、适用场景与一系列实操最佳实践与使用技巧。结论是：Cloud Code 本质上是一个“终端型”的智能编程代理，依赖于模型驱动的工具调用与交互式搜索（agentic search），适合加速新项目原型、熟悉/重构大型代码库、自动化测试/提交流程和嵌入 CI/CD 等场景。要高效使用它需掌握 cloud.md（或 claude.md）文件写法、权限管理、上下文管理与小步迭代测试等操作习惯，同时理解其轻量化设计与安全边界。

# 3. 按照主题来梳理

## 3.1 演讲者与背景

- 演讲者自我介绍与加入缘由。演讲者名为 Cal，约一年半前加入 Anthropic，参与组建名为 Applied AI（应用人工智能）的小组。该团队的目标是帮助客户与合作伙伴在 Claude（模型）上构建优秀产品与功能。他日常工作大量涉及 prompting（提示工程）以从 Claude 获取高质量输出，并兼具编码兴趣，喜欢启动各种项目。一次偶然体验 Cloud Code（在周末把它用于个人笔记应用开发）彻底改变了他的编码方式与效率，从而促成他加入 Cloud Code 团队，成为核心贡献者，负责系统提示（system prompts）、工具描述、工具结果格式化以及评估方法学的工作。
- 通过内部排行榜进入团队的经历。Cal 提到自己在试用 Cloud Code 时，短时间内使用量在公司内部的排行榜上攀升，借此机会认识了 Boris、Cat 和早期的 Cloud Code 团队成员，并提出自己可以贡献 prompting 方面的专业能力，最终成为团队成员之一。这说明产品内部早期迭代与员工试用能带来快速反馈回路，也体现出团队对 prompt 与工具交互质量的重视。
- 他在团队中的职责与关注点。Cal 主要负责优化如何提示 Claude、如何设计工具（tools）的描述、如何记录工具返回结果（tool results）的格式，以及如何评估改动是否真正提升了 Cloud Code 的表现。他强调评估体系的重要性，即修改 Prompt 时如何验证改进不会反而破坏 Cloud Code 的功能或安全边界。

## 3.2 Cloud Code 是什么以及核心架构与运作方式

- 核心比喻与定位。Cal 把 Claude Code 比作“那个终端里无所不能的同事”，也就是那类不碰 GUI、纯在终端完成一切操作的牛人工程师。Cloud Code 的设计念头是把这种终端型专家的能力以 agent（智能代理）的形式放在用户电脑上，使开发者可以通过自然语言驱动终端操作、文件编辑、运行 CLI（命令行界面）工具等。
- “简单可行的方案”（the simple thing that works）。Anthropic 的产品哲学是优先做“简单可行”的方案。对于 Cloud Code，这体现在它被实现为一个相对“纯粹”的 agent：几段指令 + 一组强大的工具，然后让模型循环运行直到判断任务完成。工具集合包括文件创建/编辑、执行终端命令、调用外部 MCP（Model-connected Process）等，模型在这些工具之间来回调用以完成任务。
- 代码库理解方式：不是索引而是探索。与常见会将整个代码库索引、生成 embeddings 并做 RAG（retrieval-augmented generation）检索的方案不同，Cloud Code 让模型像一个新加入团队的工程师那样“探索”代码库：使用传统文件搜索工具（比如 glob、grep、find 等）进行“agentic search”（代理式搜索），模型根据搜索结果再决定下一步要看哪些文件、走哪些路径，逐步构建对代码库的理解。这种动态探索避免了提前全量索引带来的复杂性与维护成本。
- 辅助层：轻量 UI、权限与安全。Cloud Code 在 agent 之上构建了一个轻量级的交互界面，用户可以实时看到模型在做什么（文本滚动、工具调用记录等）。同时引入权限机制：对只读操作默认允许，但一旦模型要写文件、运行可能改动系统的 bash 命令或执行敏感操作，UI 会要求用户授权（选择始终允许、拒绝或临时允许）。这种权限控制是产品安全与用户信任的关键一环。此外，Cloud Code 支持在 Anthropic 提供的 API 之外，也能原生连接 AWS/GCP 等云平台的模型部署方式，为更保守或合规性需求的用户提供选择。
- 设计取舍的含义。Cloud Code 的设计选择（不索引、依赖动态搜索、轻量化工具集合）带来易用与安全的好处，但也意味着其行为高度依赖于模型的搜索决策与 prompt 指令，产品需要在工具语义、权限控制与提示策略上投入大量工程与调优工作，以确保在真实代码库中可预测地完成任务。

## 3.4 关键最佳实践：如何配置与日常使用

- 使用 claude.md / cloud.md（配置与约束共享文件）。Cloud Code 本身缺少长期记忆，团队需要通过放置特定的说明文件（演讲中称为 cloud.md 或 claude.md）将项目背景、运行测试的方法、项目结构说明、风格指南等上下文直接注入到 agent 启动时的 prompt 中。该文件可以放在项目根目录供整个团队共享，也可以放在用户的 home 目录用于常驻指令。建议把如何跑单元测试、目录结构说明、关键模块位置、常用内置工具的调用方法等写清楚，以减少 agent 反复犯错或重复探索的成本。
- 权限管理与 autoaccept（自动接受）策略。默认对读取类操作不干预，但对写入或执行潜在危险命令会弹 UI 询问。用户可以配置常用命令如 npm run test 为“始终允许”，以减少频繁确认的摩擦；也支持按需临时允许以保证安全。还有 autoaccept 模式（例如按 Shift+Tab）会让 agent 连续工作，不再逐步等待确认，适合信任度高且无需频繁人工插手的场景。
- CLI 工具优先使用本机安装版。对于外部服务与工具（比如 GitHub 的 GH CLI），经验上优先在本机安装官方 CLI，然后让 Cloud Code 直接调用，这比通过远程 MCP 服务通常更稳健。若企业内部有特定 CLI（Anthropic 的内部工具例：coup），应该把调用方法记到 cloud.md 里，让 Claude 知道如何使用。
- 上下文窗口与 compact（压缩）策略。Cloud Code 会随着对话与工具调用积累上下文，Anthropic 的模型上下文窗口可以到 200k tokens，长时间会提示接近上限。此时有两种操作方式：/clear（清空）会重置会话（保留 cloud.md）；/compact（压缩）会让模型把当前会话的要点总结为一条用户消息，作为后续会话的种子，从而继续工作且节省上下文空间。演讲者强调 compact 的调优花了很多心力，让用户在长会话中仍能保持高效。
- 规划、待办与小步迭代。使用 Cloud Code 时先让模型生成“修复计划”或“实施方案”，并检查其步骤与可行性，能避免盲目写文件。Cloud Code 会自动生成任务 to-do 列表，用户应持续监视并在发现偏差时按 Esc 中断并重新调整路线。结合 TDD（测试驱动开发）、频繁提交（commit）与跑测试，能在模型可能“跑偏”时快速回滚并定位问题。
- 截图与多模态输入。Claude（模型）支持多模态输入，可以把截图或 mock 图片直接粘贴给模型用于界面实现或调试。这在 UI/前端工作中非常有用。
- 高级用法：多云并行、MCP 服务器和无头化自动化。经验丰富的团队会同时对接多个云环境（演讲者知道有人同时连接四个云）来做跨环境编排。若标准工具能力不足，可接入 MCP 服务器来扩展能力。Cloud Code SDK 允许无头（headless）运行，使其可嵌入 GitHub Actions 等自动化流程，实现程序化的编码 agent。

## 3.5 新特性与演讲者的实时演示要点

- 模型切换与 slashmodel。用户可以在会话中通过 /slashmodel 查看当前使用模型（默认为 Sonnet）并切换到其他模型（如 Opus）。保持合适模型对不同任务的表现至关重要。
- “在工具调用之间思考”（thinking between tool calls）。以前模型在工具调用与调用之间的“思考”能力有限，但从 Cloud 4 开始，模型可以在工具调用间进行显式的、更长时间的思考（演讲中称作“think hard”或 extended thinking），并通过界面上较淡的灰色文本来表示“思考阶段”。这使得在进行复杂的多步检索与决策时，模型能更系统地组织信息并给出更合理的下一步计划。
- 编辑器集成：VS Code 与 JetBrains。Cloud Code 提供与主流编辑器的深度集成，模型能感知当前打开的文件并直接在编辑环境中工作，这进一步提升了本地开发体验。
- 发布渠道与变更日志。Cloud Code 的功能在快速迭代，团队在 GitHub 上开设了公开项目（Claude Code under Enthropic），并通过 changelog 发布更新。演讲者建议定期查看变更日志以了解新功能和行为改动。

## 3.6 常见问题与应对策略（Q&A 摘要）

- 多个 cloud.md 文件的解析策略。默认只读取当前工作目录下的 cloud.md 以避免 monorepo 中的大量文件同时被加载导致上下文爆炸。但当 agent 在搜索过程中发现子目录有相关的 cloud.md，会建议读取那个子目录的说明。用户可以把通用指令放在 home 目录的 cloud.md，并在项目的 cloud.md 中通过引用其他文件（例如使用 @ 引用语法）来组合上下文。
- 模型不遵守 cloud.md 的情况。演讲者承认模型之前存在“喜欢插入解释性内联注释”的问题，即便 prompt 中明确禁止也会发生。Cloud 4 对此进行了改进，模型遵从指令的能力显著提升。建议用户在切换到新版模型后重新审视 cloud.md 内容，删减或更新不再需要或导致冲突的指令，以提高遵从度。
- 多 agent 协作与上下文共享的实现。当前实现以“做简单可行的事”为原则，尚未提供复杂的多 agent 原生上下文路由机制。一个实用的替代方案是让多个 agent 写入共享的 Markdown 文件（例如 ticket.md），让其他 agent 读取该文件来实现间接的上下文传递。未来产品可能会提供更正式的并行/联动支持。

# 4. 框架 & 心智模型（Framework & Mindset）

- “Agent-as-a-terminal-expert”心智模型（至少 500 字）。把 Cloud Code 看作放在桌边的那个“终端专家”同事：他们不看 GUI，只在终端里完成所有工作，熟练使用 Git、Vim、各种 CLI 工具和 shell 脚本。将 Cloud Code 建成这样一个代理意味着你在设计交互时应始终把终端命令、文件结构与 CLI 工具链放在核心位置，而非把模型当作单纯的文本生成器。基于此心智模型，你的设计与日常使用逻辑会倾向于：
    - 优先将项目常用操作暴露为 CLI，方便 agent 直接调用（例如测试、构建、部署脚本）。
    - 把项目约定、运行命令、模块说明写进 cloud.md，让 agent 启动时带入这些“地理信息”，就像新人第一次坐在工位上被同事口头告知一样。
    - 在交互上更偏向“让 agent 操作终端并观察其操作日志”的模式，而非把模型的每一句话都当作最终答案。你会考虑在 agent 运行过程中实时监控、按需中断（按 Esc）并调整策略。
    - 将权限设置与危险操作隔离：对只读检索放手，对涉及写入/执行高风险命令要求明确授权或采用 sandbox 手段。
    - 以“小步快跑、频繁回滚”为惯常开发节奏：模型执行会有偏差风险，频繁运行测试、提交 commit、保持可回滚的最小变更，能有效降低损失。
    - 重视“计划先行”的习惯：在实际写文件前让 agent 先做搜索、列出 2-3 个实现方案并生成 to-do 列表，这比让模型直接动手往往更稳妥。
- “Simple thing that works” 产品思维（至少 500 字）。Anthropic 在 Cloud Code 上遵循的工程与产品原则是做“简单且可行的事情”。把这个原则抽象成可遵循的步骤/方法论：
    - 识别核心能力并把复杂度推到外部：Cloud Code 的核心是语言模型 + 一套明确的工具（文件、终端、MCP）。不要在初期引入全文索引、复杂的知识库嵌入等机制，而是尽量利用模型的搜索/理解能力与传统文件检索工具来解决代码理解问题。对产品团队意味着优先开发与打磨 agentic search 的交互体验，而不是从一开始试图覆盖所有边界用例。
    - 明确权限与安全界面：在 agent 能力边界之外引入清晰的权衡。对 read-only 操作默认开放，对 write/execute 操作默认需要确认，并提供详细的操作预览。把安全控制做成易用配置项（autoaccept 白名单、交互中断键等），能在保证可用性的同时降低事故率。
    - 以可组合、易替换的模块为单元。把 cloud.md、CLI 工具、MCP 接口和 compact 机制设计成可独立演进的模块：云端模型可以切换（/slashmodel），上下文管理可以清空或压缩（/clear、/compact），权限可以细粒度配置。这样的设计便于未来替换模型、扩展工具链或改进上下文策略时不破坏整体使用体验。
    - 把可解释性放在产品层面。由于 agent 会在终端做出一系列命令与文件修改，产品应记录每一步的工具调用与模型输出，让用户能回溯 agent 的决策路径。这样既方便调试，也方便在团队间进行知识传递（例如将工作过程写成 ticket.md 以供下一个人接手）。
    - 快速迭代并重视用户反馈。Anthropic 通过内部排行榜、早期员工试用与公开 GitHub 项目获得大量反馈，按“simple thing that works”逐步扩展功能集。这提示我们在设计 AI 辅助开发工具时应先交付能解决明显痛点的最小可行方案，再基于实际使用数据逐步优化复杂能力（如多 agent 协作、并行化、MCP 扩展等）。
    - 保障实验与安全并重。允许用户在信任的环境（本地或特定云）里尽情试验 Cloud Code，同时通过权限、沙箱与审计机制降低误操作风险。产品层面的策略包括：限制默认可执行权限、显式记录所有敏感操作与提供回滚路径。

# 总结

Cloud Code 是以终端为核心、以模型驱动工具调用的轻量化编码代理，适用于代码库探索、快速原型、在既有项目中增量开发、自动化部署与故障排查等多种场景。高效使用它的关键包括编写详尽的 cloud.md（或 claude.md）以注入上下文、合理配置权限与自动接受策略、优先使用本地 CLI、掌握上下文压缩/清空机制、坚持小步迭代并结合测试、利用多模态输入以及在需要时通过 MCP 或 SDK 实现无头化集成。产品设计遵循“做简单且可行的事”的原则，推荐以稳健的交互与可解释的工具调用记录为基础，逐步扩展更复杂的并行或多 agent 功能。
