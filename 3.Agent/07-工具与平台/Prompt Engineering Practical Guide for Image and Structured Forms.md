# 提示工程实用指南 —— 面向图像与结构化表单的应用示例

## 概述

- 提示工程是与大规模语言模型（LLM）沟通、使其完成特定任务的技术。核心在于：清晰指令、必要上下文、合理信息组织与迭代优化。
- 本文以"为瑞典汽车保险理赔读取事故报告表单与手绘草图，并判断责任归属"为例，归纳一套可直接用于知识库的实战方法论与模板。

## 典型问题与目标

- 输入：固定格式的表单（17 个复选项行，左右两列分别代表车辆 A/B）、手绘草图（人画，可能潦草）、语言为瑞典语。
- 目标：自动化读取表单与草图，提取事实、给出事故摘要、明确责任判定，并输出可机器解析的结构化结果（XML/JSON）。
- 要求模型：不凭空编造、不在不确定时猜测、在做出判断时引用证据来源（例如"基于表单第 X 行的勾选"）。

## 推荐的提示结构（单次完整请求）

### 任务描述（Task Description）

- 明确模型角色与目标，例如："你是协助理赔员读取瑞典车祸表单与草图的 AI 助手。你的任务是……。"
- 指定语气与行为准则：保持事实、在不确定时拒绝判断、对所有事实性陈述给出证据引用。

### 背景与固定信息（Background / Static Context）

- 把不会变化但每次都适用的信息放在这里（建议放入 system prompt 或缓存）：表单的标题、列含义、每一行代表的项目、填写方式说明（圈、涂画、打叉等可能性）。
- 说明常见噪声与瑕疵（手写、涂改、遗漏），指导模型如何处理。

### 动态内容（Dynamic Content）

- 附上此次具体的表单图像、草图（可 Base64 或链接），以及任何额外文本说明。
- 明确指出这些是要被解析的主要输入。

### 逐步指令（Detailed Instructions / Reasoning Steps）

- 指定模型应遵循的分析顺序（强烈建议先读表单再看草图）。
- 明确要求：列举每一行是否勾选；如果不确定就标注"不确定"；为每一事实提供依据（例如"第 4 行左列：已打圈"）。
- 要求中间产物（evidence list / intermediate analysis）和最终结论分开提供。

### 示例（Few-shot Examples，可选但强烈推荐）

- 提供一到数个典型样例（包含输入与正确输出），尤其对边缘或易错案例要覆盖。
- 示例可以包含图像编码、解析描述与对应的结构化输出，帮助模型学习判别规则。

### 输出格式与约束（Output Formatting）

- 明确指定机器可解析的输出格式（XML/JSON），并给出严格的模版。
- 要求最终回答只包含指定格式（或明确在哪个标签内包含最终判定），便于后续自动化处理。

### 最后提醒（Final Reminder）

- 再次强调不编造、不猜测、只在有证据时断定责任；并在每条结论后标注证据来源。

## 为什么把固定信息放到 system prompt（或缓存）

- 固定表单结构、字段定义等在每次调用都重复发送会浪费 token。把这些长期不变的细节放在 system prompt 或用 prompt-caching，可以提高识别速度与稳定性，并减少误判率。

## 关于信息组织与标注（实用技巧）

- 使用显式分隔与标签（例如 XML-like tags）来标注不同信息块：、、等，有利于模型回溯与引用。
- 若需人机协作，可让模型"展示其步骤"（逐项列出对每一复选框的判断），但注意过度展示会造成冗长。可通过指令控制是否显示中间细节。

## 处理不确定性与避免幻觉

- 明确要求模型在证据不足时返回"无法判定"或"需人工复核"，不要允许模型用"可能"、"大概"来替代证据。
- 指示模型在每项事实后附上证据引用（如："依据：表单第 3 行，车辆 B 列有明显打叉"）。

## 输出格式示例（示范性模版）

- 结构化输出示例（可按实际需要改为 JSON）：xml
  <FINAL_VERDICT>
    <ACCIDENT_SUMMARY>简短事实摘要</ACCIDENT_SUMMARY>
    <FORM_ANALYSIS>
      <ROW id="1">
        <LEFT checked="yes/no/uncertain" evidence="说明依据"/>
        <RIGHT checked="yes/no/uncertain" evidence="说明依据"/>
      </ROW>
      ...（每行类似）
    </FORM_ANALYSIS>
    <SKETCH_ANALYSIS>结合草图的观察与推断</SKETCH_ANALYSIS>
    <FAULT_DETERMINATION>Vehicle A / Vehicle B / Both / Unknown</FAULT_DETERMINATION>
    <CONFIDENCE>高/中/低</CONFIDENCE>
  </FINAL_VERDICT>

## 分析顺序建议（保证可靠性）

1. 读取并解析表单：按行逐项判定是否标注、记录证据。
2. 根据表单构建事实库（谁在什么位置、动作信息等）。
3. 读取草图：把草图观察到的要素与事实库对齐，找一致或冲突点。
4. 做出结论，并为结论逐条列出依据（首选表单证据，其次草图支持）。
5. 若重要信息缺失则返回"需人工复核"，并列出缺失项。

## 示例提示要点（文字版模板）

- System（系统说明，长期不变）应包含：表单结构定义、每行含义、常见填写形式、不要猜测的规则、输出模版。
- User（本次任务）应包含：本次图像/文本输入、期望执行的工作（按步骤）、是否需要显示中间步骤、要返回的最终标签与格式。

## 利用示例与会话历史提升准确率

- 将历史难例与正确标注加入 system prompt（few-shot）可显著降低模型在同类难题上的错误率。
- 在人机交互场景下，保留并在必要时传入会话历史以补充上下文。

## Extended Thinking（延展思考 / scratchpad）

- 启用模型的"思考日志"（如果模型支持）可以让模型在内部记录逐步推理，有利于调试和改进提示。
- 可以把思考过程用于离线分析：找出模型常错的位置并将这些错误场景纳入示例集或 system prompt 中。

## 调试与迭代流程（实用步骤）

6. 快速原型：写出最小可用 prompt（任务+输入+期望输出格式），先做功能验证。
7. 观察错误：开启思考日志或要求显示中间步骤，找出误判原因（术语不明、顺序错、证据识别失败）。
8. 补充上下文：将表单定义、填写样式等放入 system prompt，或加入几个典型示例。
9. 调整指令：明确顺序（先表单再草图）、限定推理范围、规定不确定时的行为。
10. 生产化：固定 system prompt、启用输出格式约束、在应用端实现解析与人工复核流程。

## 常见问题与建议

- 模型"发明"细节：要求"只基于所提供输入陈述事实并给出出处"。
- 输出不一致：固定输出模版并在每次请求前校验格式。
- 模型过于冗长/过于简略：用指令限制中间步骤显示与输出长度（例如"仅列出每行判断与证据，最终结论不超过三句话"）。

## 快速检查清单（Prompt QA）

- 有明确任务与角色说明吗？
- 固定表单结构是否已放入 system prompt 或缓存？
- 动态输入（图像/表单）是否正确附上并标注？
- 是否要求模型先解析表单再看草图？
- 是否对不确定性给出明确处理方式？
- 是否指定严格的结构化输出格式？
- 是否提供了足够的示例或历史会话用于复杂或灰色案例？
- 是否开启或记录思考日志以便调试？

## 结语

- 好的提示工程是一个迭代的工程：从明确角色与规则入手、把稳定信息"固化"到 system prompt、用示例补强边缘案例、通过可解析输出与思考日志进行验证与改进。针对结构化表单 + 图像的任务，遵循"先读表单、后看草图、所有结论要给证据"的原则，能显著提升自动化判定的准确性与可审计性。
